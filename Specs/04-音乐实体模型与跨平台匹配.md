# 音乐实体模型与跨平台匹配

**状态：** 草案 v0.1  
**最后更新：** 2026-08-01  
**上级规格：** `00-系统总体设计与规格路线图.md`  
**关联规格：** `01-歌曲信息数据来源与版权边界.md`、`02-外部音乐数据接口验证.md`、`03-MVP产品规格：歌曲世界杯与音乐探索.md`

## 1. 目标

为歌曲世界杯提供唯一、稳定、可追溯的音乐实体身份，并将不同供应商的展示资源绑定到正确实体。

本规格解决以下问题：

1. 同名歌曲、翻唱、Live、Remaster、Demo 如何区分；
2. MusicBrainz 的规范元数据如何与 Apple 等 Provider 的封面、试听和外链对齐；
3. 对齐不确定时，如何避免将错误歌曲放入赛事或错误播放试听；
4. 如何让 Java 业务服务、Python Agent 和前端都使用同一套内部 ID，而不依赖供应商原始响应。

## 2. 原则

1. **实体优先。** 先确定内部规范实体，再附加外部资源；不以封面、试听 URL 或歌名文本作为身份。
2. **录音优先。** 歌曲世界杯的候选项是一个具体 `Recording`，不是模糊的歌曲标题。
3. **版本可见。** Live、Remaster、Demo、翻唱和不同艺人的同名歌必须是不同候选项。
4. **来源可追溯。** 每项外部映射记录供应商、外部 ID、匹配方法、置信度和刷新时间。
5. **宁缺毋错。** 低置信度资源不自动挂到赛事中；无试听时用外链或无试听状态降级。
6. **不存受限媒体。** 只保存合法的远程 URL、归属和使用策略，不下载或代理封面/音频。

## 3. 术语与实体层次

```text
Artist（艺人）
  └── Work（作品/创作概念，可选）
        └── Recording（具体录音版本，赛事候选的最小单位）
              └── Release Track（该录音在某个发行版中的曲目）
                    └── Release（具体发行版）
                          └── Release Group（专辑/单曲的发行概念）
```

| 实体 | 示例 | MVP 用途 |
| --- | --- | --- |
| Artist | 五月天 | 赛事所属艺人、搜索入口、推荐对象 |
| Work | 《温柔》的创作作品 | 可选；用于未来处理翻唱与不同录音关系 |
| Recording | 《温柔》录音室版 | 赛事候选、试听和偏好信号的最小单位 |
| Release Group | 《爱情万岁》专辑概念 | 专辑导览、默认封面归属 |
| Release | 某地区/日期发行的《爱情万岁》版本 | 曲目表、发行日期、具体封面 |
| Provider Mapping | Apple trackId / 将来的酷狗 songId | 外部资源定位，不作为内部主键 |

## 4. 规范数据模型

所有主实体使用内部 UUID 作为主键；如果 MusicBrainz 存在对应实体，则保存其 MBID 作为规范外部锚点。

### 4.1 核心表

```text
music_artist
  id, musicbrainz_mbid, canonical_name, sort_name,
  country_code, disambiguation, status, created_at, updated_at

music_release_group
  id, musicbrainz_mbid, title, primary_artist_id,
  type, first_release_date, status, created_at, updated_at

music_release
  id, musicbrainz_mbid, release_group_id, title,
  release_date, country_code, barcode, status, created_at, updated_at

music_recording
  id, musicbrainz_mbid, canonical_title, duration_ms,
  isrc, primary_artist_id, status, created_at, updated_at

music_release_track
  id, release_id, recording_id, disc_number, track_number,
  track_title, duration_ms

external_mapping
  id, entity_type, entity_id, provider, external_id,
  external_url, match_method, confidence, mapping_status,
  provider_payload_hash, refreshed_at, expires_at, created_at, updated_at

media_asset
  id, entity_type, entity_id, provider, asset_type,
  remote_url, attribution, usage_policy, available,
  refreshed_at, expires_at, created_at, updated_at
```

### 4.2 关键约束

- `musicbrainz_mbid` 在同一实体表中唯一，允许为空；
- `(provider, entity_type, external_id)` 唯一；
- `music_release_track` 的 `(release_id, disc_number, track_number)` 唯一；
- `music_recording.isrc` 可为空；非空 ISRC 不强制全局唯一，因为数据源可能存在录入误差或再发行例外；
- `external_mapping` 不保存完整供应商原始 JSON，只保存必要字段摘要和内容哈希；
- `media_asset` 不保存媒体二进制、歌词全文或下载地址。

### 4.3 映射状态

| 状态 | 含义 | 可否用于赛事 |
| --- | --- | --- |
| `verified` | ISRC 精确匹配或人工确认 | 可以 |
| `auto_linked` | 规则引擎高置信自动匹配 | 可以，但需保留审计信息 |
| `candidate` | 有候选，但未达到绑定阈值 | 不可以自动使用 |
| `rejected` | 已证实不匹配 | 不可使用 |
| `stale` | 资源过期或供应商不可用 | 不可作为新资源，已保存赛事需降级展示 |

## 5. Provider 统一契约

每一个供应商必须通过 Provider Adapter 接入。业务服务、Agent 和前端不得直接依赖供应商特有字段。

```text
search_artists(query, region) -> ProviderArtistCandidate[]
search_recordings(query, artist_hint, region) -> ProviderRecordingCandidate[]
get_recording_detail(external_id, region) -> ProviderRecordingDetail
get_release_detail(external_id, region) -> ProviderReleaseDetail
get_preview(external_id, region) -> ProviderPreview | unavailable
```

统一候选 DTO 至少包含：

```json
{
  "provider": "apple_itunes",
  "externalId": "1207222593",
  "externalUrl": "https://...",
  "title": "温柔",
  "artistNames": ["五月天"],
  "albumTitle": "步步自选作品辑 1999-2013",
  "durationMs": 0,
  "releaseDate": "2013-12-30",
  "isrc": null,
  "artworkUrl": "https://...",
  "previewUrl": "https://...",
  "usagePolicy": "apple_promotional_content"
}
```

DTO 中的字段可为空；空值不得被模型或调用方自动补造。

## 6. 匹配策略

### 6.1 匹配顺序

1. 查询已有 `external_mapping`；若存在可用映射，直接复用。
2. 使用 MusicBrainz 解析用户输入，确定 `Artist`、`Recording` 和可能的 `Release`。
3. 用规范标题、主艺人别名和地区向 Provider 查询候选。
4. 对候选执行确定性规则匹配和评分。
5. 达到阈值则创建映射；否则保留候选或要求用户确认。

### 6.2 匹配优先级

| 优先级 | 条件 | 结果 |
| ---: | --- | --- |
| 1 | 相同 Provider Mapping 已存在且资源可用 | 直接使用 |
| 2 | 两端均有相同 ISRC | `verified` |
| 3 | 标题、主艺人、时长均高度一致，且版本/专辑信息不冲突 | 可能 `auto_linked` |
| 4 | 标题、主艺人一致，但时长或专辑不完整 | `candidate`，不自动用作试听 |
| 5 | 仅歌名相同，或主艺人/版本冲突 | `rejected` 或保留供用户选择 |

### 6.3 规范化规则

匹配前按以下规则生成仅用于比较的规范化字段，原始展示名称不得被覆盖：

- Unicode 规范化，统一全角/半角与空白；
- 简体/繁体建立等价比较键；
- 大小写不敏感；
- 去除不影响身份的标点；
- 解析并单独保存 `feat.`、`with`、`&` 等合作艺人信息；
- 识别 `live`、`remaster`、`demo`、`acoustic`、`instrumental` 等版本标记；
- 时长以毫秒比较，默认容差为 3 秒；
- 绝不因为“封面相同”而判定为同一录音。

### 6.4 默认评分模型

只有不存在 ISRC 精确匹配时才使用评分模型：

```text
title_score           0.45
primary_artist_score  0.35
duration_score        0.15
release_score         0.05
```

- `score >= 0.93` 且第一、第二候选差值 `>= 0.08`：创建 `auto_linked`；
- `0.75 <= score < 0.93`：创建 `candidate`，等待用户确认或人工审核；
- `score < 0.75` 或存在版本冲突：不创建映射；
- 任一版本标记冲突（如 studio 与 live）时，不得自动绑定，即使标题和时长接近。

评分模型是规则系统，不由 LLM 决定。阈值与权重必须可配置、可记录版本、可离线评估。

## 7. 封面、试听与外链绑定规则

### 7.1 试听

- 试听资源绑定到 `music_recording`；
- 只有 `verified` 或 `auto_linked` 的 Provider Mapping 才可展示站内试听；
- 试听资源不可下载、缓存、代理或写入向量库；
- 资源缺失、过期、地区不可用时，显示“暂无试听”及可用的官方外链；
- 同一歌曲多个发行版存在试听时，优先使用与当前 `Recording` 绑定且地区可用的资源。

### 7.2 封面

- 封面优先绑定 `music_release` 或 `music_release_group`，而非录音；
- 歌曲卡应优先展示当前赛事候选对应发行版的封面；缺失时回退到发行组封面，再回退到 Provider 合规远程封面或占位图；
- 封面只能保存远程 URL、归属和使用策略；
- 对受版权限制的封面，不得叠加自身品牌、裁剪后再分发或写入对象存储。

### 7.3 外链

外链同样属于 Provider Mapping。它必须指向当前匹配的歌曲或专辑页面，不能以艺人主页代替具体歌曲链接，除非供应商没有歌曲级链接。

## 8. 版本消歧与赛事候选规则

### 8.1 默认排除

创建艺人赛事时，候选池默认排除：

- 同一 `Work` 的近重复录音；
- 现场版、Remaster、Demo、伴奏、纯音乐版、卡拉 OK 版；
- 标记为不可播放且无外链的录音；
- 主艺人不是目标艺人的同名歌曲。

### 8.2 允许但需显式标注

- 合作歌曲：目标艺人为主艺人或明确合作艺人时可纳入，卡片需标注合作关系；
- 翻唱歌曲：可纳入，但需标注“翻唱”；
- 同曲不同录音：只有用户在自选候选池中明确选择时才允许同时出现；
- Live/Remaster 专题赛：后续扩展，MVP 不提供。

### 8.3 冲突处理

当用户搜索或自选遇到同名多版本时，前端必须展示：标题、艺人、专辑、版本标签、发行年份和时长（可用时）；不得只显示歌名让用户盲选。

## 9. 运行流程

### 9.1 用户搜索艺人

```text
输入“五月天”
  → MusicBrainz Artist Search
  → 返回规范艺人候选及置信度
  → 用户选择艺人
  → 查询本地已缓存的 Recording / Release 数据
  → 不足时异步补充 Provider 数据
```

### 9.2 生成候选歌曲

```text
目标艺人
  → 取得可用的规范 Recording 集合
  → 按版本规则去重
  → 经典模式：热门/随机/自选
  → 探索模式：将候选元数据与已验证事实交给 Agent 策展
  → 用户确认 16 或 32 首候选
  → 创建不可变赛事快照
```

### 9.3 映射无法确认时

```text
规范 Recording
  → Provider 候选评分不足
  → 保存为 candidate（可选）
  → 不绑定试听/封面
  → 显示可用的搜索外链或占位资源
  → 不阻塞赛事与投票
```

## 10. 缓存、刷新与审计

- 所有外部读取必须先查本地缓存；
- Provider 响应的刷新周期由配置管理，不写死在业务代码中；
- 每次刷新记录 `provider_payload_hash`、`refreshed_at`、`expires_at` 和结果状态；
- 已开始赛事使用创建时的实体快照，后续 Provider 刷新不得篡改历史赛程；
- 失效的预览 URL 可以在历史赛事中显示为不可用，但不得改变用户投票和冠军；
- 管理端后续应支持查看、确认、拒绝 `candidate` 映射及审计匹配原因。

## 11. Agent 与实体服务的边界

| 责任 | 实体服务 / Provider | Agent |
| --- | --- | --- |
| 用户输入实体消歧 | 规则与用户确认 | 可提出搜索关键词，但不最终判定 |
| 录音与 Provider 资源匹配 | 确定性规则引擎 | 不参与评分或写映射 |
| 版本去重 | 规则引擎 | 在合规候选池内进行策展 |
| 赛事快照 | Java 业务服务 | 只读 |
| 音乐解释与推荐 | 提供已验证实体/事实 | 生成有来源的解释和推荐 |

## 12. 验收标准

### 12.1 实体与映射

- [ ] 可用 MusicBrainz MBID 唯一定位艺人、录音、发行组和发行版；
- [ ] 内部业务记录只引用内部 UUID，不将 Apple/其他 Provider ID 当作主键；
- [ ] 相同 ISRC 的跨 Provider 资源自动标记为 `verified`；
- [ ] 仅歌名相同的不同艺人歌曲不会自动绑定；
- [ ] studio 与 live/remaster/demo 冲突不会自动绑定；
- [ ] 低置信度候选不会被用作站内试听。

### 12.2 资源与降级

- [ ] 有效映射的试听可返回来源、外链与使用策略；
- [ ] 无试听或试听失效时，赛事仍可正常完成；
- [ ] 封面缺失时按发行版、发行组、合规 Provider、占位图顺序回退；
- [ ] 系统不保存任何外部音频或受限封面二进制。

### 12.3 赛事快照

- [ ] 用户确认后的 16/32 首候选池指向不同的规范 `Recording`；
- [ ] 开赛后 Provider 数据刷新不会改变已有对阵、投票或历史展示身份；
- [ ] 用户自选同曲多版本时，界面清晰标注并要求显式确认。

## 13. 不在本规格范围内

- 具体数据库 DDL、ORM、迁移脚本和 Repository 实现；
- Java 对外 HTTP API、鉴权和事务实现；
- Provider 的具体网络重试参数与熔断策略；
- Knowledge Claim / Milvus 文档的数据模型；
- Agent 的状态机、Prompt 和模型选择；
- 正式接入酷狗、QQ 音乐或其他商业 Provider 的合同与 SDK 细节。

这些内容分别由 Java 业务服务、Agent 工作流、知识库和部署规格定义。
