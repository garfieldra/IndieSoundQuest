# MVP 产品规格：歌曲世界杯与音乐探索

**状态：** 草案 v0.1  
**最后更新：** 2026-08-01  
**上级规格：** `00-系统总体设计与规格路线图.md`  
**依赖规格：** `01-歌曲信息数据来源与版权边界.md`、`02-外部音乐数据接口验证.md`

## 1. 一句话定义

用户可以为一位艺人举办一场私有的歌曲世界杯；系统记录真实选择，Agent 再将这些选择转化为有证据、有边界的音乐偏好总结和下一步探索建议。

## 2. 要解决的问题

### 2.1 用户痛点

1. 喜欢一位艺人，却难以从大量歌曲中理清自己真正偏爱的作品和创作阶段。
2. 流媒体推荐能给出很多歌，但通常无法解释“为什么推荐”，也无法把单次选择沉淀为长期偏好。
3. 用户想探索新音乐，但很难用专业术语描述自己的听感偏好。

### 2.2 MVP 的解决方式

把“选择困难”变成低门槛的二选一游戏，把每次选择变成明确的偏好信号；Agent 在赛后而非赛中主导解释、推荐和引导探索。

## 3. 用户与使用场景

| 用户 | 场景 | 目标 |
| --- | --- | --- |
| 熟悉某位艺人的听众 | “我想选出五月天最喜欢的一首歌。” | 获得有趣、完整的私人赛事体验 |
| 对艺人有兴趣的新听众 | “我想通过几轮选择，看看自己会喜欢这位艺人的哪一面。” | 找到适合自己的入门方向 |
| 有持续探索意愿的用户 | “我已经玩过几场，想知道自己整体喜欢怎样的音乐。” | 获得音乐偏好总结和下一步推荐 |

## 4. 产品目标与非目标

### 4.1 MVP 目标

1. 用户可通过搜索选择一位艺人，并创建一场 16 或 32 首歌的私有赛事。
2. 用户可在每轮查看歌曲基础信息、封面和合规的短试听入口后投票。
3. 用户可完成淘汰赛并得到冠军、完整晋级图和本场赛事总结。
4. 探索世界杯可由 Agent 挑选覆盖艺人不同阶段/风格的候选歌曲，并生成个性化推荐。
5. 系统可将多场有效赛事汇总为“音乐偏好报告”，但只描述音乐偏好，不推断现实人格或敏感属性。
6. 所有与音乐背景有关的关键事实都提供来源或明确标识为建议/推断。

### 4.2 MVP 非目标

- 完整歌词、完整歌曲播放、下载和音频托管；
- 公开排行榜、好友对战、评论、分享广场等社交能力；
- 小组赛、遗珠复活赛、跨艺人混合赛、实时多人赛事；
- 从音乐偏好推断教育、职业、收入、心理状态或真实人格；
- 直接使用非公开或未授权的国内音乐平台接口；
- 自动宣称“用户一定喜欢”或“某首歌客观上更好”。

## 5. 核心概念

| 概念 | 定义 |
| --- | --- |
| 赛事（Tournament） | 围绕一位艺人创建的一次私有歌曲淘汰赛 |
| 候选池（Candidate Pool） | 参与赛事的歌曲录音版本集合 |
| 对局（Match） | 两首歌曲之间的一次二选一 |
| 投票（Vote） | 用户明确选定的胜者；是偏好分析的原始信号 |
| 经典世界杯 | 用户主要为了娱乐和选出本命歌而创建的固定赛程 |
| 探索世界杯 | Agent 以了解用户偏好和引导探索为目标策展候选池的赛事 |
| 本场偏好总结 | 只基于单场赛事生成的低置信度音乐选择总结 |
| 整体偏好报告 | 基于多场赛事生成的跨艺人音乐偏好总结 |

## 6. MVP 功能范围

### 6.1 模式一：经典歌曲世界杯

用户流程：

```text
搜索艺人
  → 选择赛事规模（16 / 32 首）
  → 选择候选来源（热门 / 随机 / 自选）
  → 确认候选池和赛程
  → 每轮试听并投票
  → 产生冠军
  → 查看晋级图与本场总结
```

规则：

- 使用单败淘汰赛；16 首需要 15 次有效投票，32 首需要 31 次有效投票；
- 首版不做平票；用户必须选择一首歌才可让对局结束；
- 用户可退出并稍后继续，赛程和已投票结果不可被 Agent 改写；
- 用户可在赛事开始前调整候选歌曲；开始后候选池和对阵固定；
- 用户可以中止赛事；中止赛事不进入整体偏好报告；
- 冠军代表当前用户在当前赛事的选择，不构成公共排行或客观评价。

候选来源的 MVP 定义：

| 来源 | 说明 |
| --- | --- |
| 热门 | 由已接入供应商的排序信号或人工维护的代表作集合生成 |
| 随机 | 从符合去重/版本规则的该艺人候选库中随机抽取 |
| 自选 | 用户从搜索结果中手动选择 16 或 32 首 |

### 6.2 模式二：探索世界杯

探索世界杯保留淘汰赛玩法，但加入 Agent 的候选策展和赛后导览。

用户流程：

```text
选择艺人
  → 选择目标（“随便认识一下” / “找我的入门方向”）
  → 选择赛事规模（默认 16 首，可选择 32 首）
  → Agent 生成有区分度的候选池，并说明覆盖维度
  → 用户确认后开赛
  → 每轮试听并投票，可选标记原因
  → Agent 生成本场偏好总结、同艺人下一站及相近艺人推荐
```

Agent 的候选策展约束：

- 候选池应覆盖至少两个创作阶段或作品面向；
- 默认不同时放入同一歌曲的 Live、Remaster、Demo、伴奏等近重复版本；
- 不得因资料不足虚构作品风格或创作背景；
- 必须给出简短的“本场会帮你区分什么”说明，例如“更偏早期摇滚张力，还是后期内省氛围”；
- 用户拥有最终确认候选池的权利。

可选投票理由仅包含音乐维度：`旋律`、`节奏`、`氛围`、`人声`、`编曲`、`歌词感受`、`说不清`。该理由为补充信号，用户不填写不影响比赛。

### 6.3 赛后结果页

每场已完成赛事必须展示：

1. 冠军歌曲与完整晋级路径；
2. 前四名歌曲；
3. 本场赛事候选池和用户每轮选择；
4. 本场偏好总结；
5. 若为探索世界杯：3–5 条下一步推荐；
6. 推荐依据、关联音乐实体和可用资料来源；
7. “再办一场”与“查看整体偏好报告”入口。

## 7. 偏好报告与推荐边界

### 7.1 本场偏好总结

完成一场赛事后即可生成，但必须标注为“仅基于本场选择”。允许输出：

- 在该艺人作品中，用户更常选择哪个时期、专辑或风格面向；
- 用户在本场更常选择的音乐标签或显式投票理由；
- 该艺人的下一首/下一张专辑探索建议。

不允许输出：

- “你是内向/外向、受过何种教育、处于何种心理状态”；
- 将一次赛事结论泛化成用户稳定、永久的审美身份；
- 没有数据来源支撑的音乐事实。

### 7.2 整体偏好报告

触发条件：至少完成 **3 场赛事且包含不少于 20 次有效投票**。未达到条件时，页面只展示“偏好信号仍在积累中”。

整体报告允许包含：

- 已探索的艺人、年代、语言、流派和作品面向分布；
- 可解释的偏好维度，如“更常选择氛围感强的作品”“更愿意从深藏曲目继续探索”；
- 置信度与证据量，如“基于 4 场赛事、27 次选择”；
- 3–5 条未探索歌曲、艺人或专辑建议，且每条附推荐理由。

所有总结都应使用“本系统观察到”“在已完成赛事中”等限定措辞，并允许用户删除历史后重新生成。

### 7.3 推荐的最低要求

每条推荐必须同时具备：

```text
推荐对象（歌曲 / 艺人 / 专辑）
推荐类型（同艺人延伸 / 相近艺人 / 入门路线）
推荐理由（关联到用户的明确选择）
音乐依据（共享的艺人、制作人、流派、时期、标签或已验证背景事实）
至少一个来源或明确的“基于用户选择”标识
```

## 8. 页面与交互

| 页面 | 核心内容 | MVP 行为 |
| --- | --- | --- |
| 首页 | 搜索艺人、选择经典/探索模式、最近赛事 | 可开始赛事；无需社交内容 |
| 赛事创建 | 艺人信息、规模、候选来源/目标、候选池确认 | 创建草稿；开始前可修改 |
| 对局页 | 两张歌曲卡、封面、歌曲/专辑信息、试听入口、投票按钮、进度 | 投票后推进到下一对局；保存进度 |
| 赛事结果 | 冠军、晋级图、本场总结、推荐 | 可查看推荐理由与资料来源 |
| 偏好报告 | 整体偏好、证据量、推荐、删除入口 | 未达阈值时展示积累进度 |
| 历史赛事 | 已完成/进行中/中止的私有赛事 | 可继续进行中赛事、删除历史 |

对局页原则：比赛过程中不弹出冗长的 Agent 对话，也不通过生成式话术干扰用户投票；只提供必要信息、试听与可选理由。Agent 的主要价值集中在赛前策展和赛后解释。

## 9. Agent 行为规格（产品层）

### 9.1 可调用的能力

| 能力 | 用途 | 输出约束 |
| --- | --- | --- |
| 音乐实体检索 | 确认艺人、歌曲、专辑及版本 | 返回规范实体与置信度 |
| 外部音乐资源查询 | 获得封面、试听、外链 | 只使用合规 Provider 返回的资源 |
| 网络资料查询 | 查找官方资料、采访、可信媒体 | 记录来源，不复制受版权全文 |
| Milvus 知识库检索 | 召回已审核的音乐事实 | 返回事实、来源、审核状态 |
| 偏好分析 | 将赛事选择转化为可解释信号 | 不推断敏感属性 |
| 推荐与路线规划 | 生成下一步歌曲/艺人/专辑建议 | 每项建议必须给出理由与证据 |

### 9.2 Agent 不可做的事

- 修改已开始赛事的对阵、候选池或投票结果；
- 将完整歌词、短试听音频或平台受限内容写入长期知识库；
- 在没有来源时把猜测表述为事实；
- 生成公开排行、对用户进行人格评价或鼓励用户公开敏感偏好。

## 10. 数据归属（产品级）

| 数据 | 所属 | 生命周期 |
| --- | --- | --- |
| 音乐实体与 Provider 映射 | 系统数据 | 可缓存、可刷新；不等于拥有音乐内容 |
| 赛事草稿、赛程、投票 | 用户业务数据 | 用户可继续、查看、删除 |
| 本场偏好总结 | 由赛事派生的用户数据 | 删除赛事后应重新计算或失效 |
| 整体偏好报告 | 聚合派生数据 | 可随赛事变动重新生成 |
| 资料来源与审核事实 | 系统知识数据 | 保留来源和审核状态 |

用户未登录时，可以创建临时赛事；临时赛事仅保存在当前浏览器会话。保存跨设备历史和整体偏好报告时，需要登录。具体登录方案由 Java 业务服务规格定义。

## 11. MVP 验收标准

### 11.1 经典世界杯

- [ ] 用户可搜索并选择一个存在的艺人；
- [ ] 用户可创建 16 首和 32 首单败淘汰赛；
- [ ] 开赛前可查看并调整候选池；
- [ ] 开赛后所有对局可恢复，刷新页面不会丢失投票；
- [ ] 每次投票仅影响当前对局和后续晋级关系；
- [ ] 完成后冠军、前四和晋级图正确；
- [ ] 用户可中止并删除私有赛事；
- [ ] 无公开排行、好友、评论或分享广场入口。

### 11.2 探索世界杯与 Agent

- [ ] Agent 生成的候选池没有近重复录音版本；
- [ ] 候选池说明至少列出一个可验证的覆盖维度；
- [ ] 用户可在 Agent 生成后确认或替换候选歌曲；
- [ ] 完赛后生成本场偏好总结，且明确标注证据范围；
- [ ] 推荐结果包含对象、理由、音乐依据和来源/用户选择标识；
- [ ] Agent 不输出人格、教育、心理或其他敏感属性推断；
- [ ] 没有可用试听时，页面降级为外部收听链接，不阻塞赛事。

### 11.3 整体偏好报告

- [ ] 未满足 3 场赛事和 20 票时，不生成稳定整体结论；
- [ ] 达到阈值后，报告展示赛事数、投票数和结论置信边界；
- [ ] 删除赛事后，整体报告能重新计算；
- [ ] 用户可删除所有赛事与偏好数据。

## 12. 后续扩展（不进入 MVP）

1. 小组赛、复活赛和更大规模赛事；
2. 专辑世界杯、流派探索赛、跨艺人主题赛；
3. 基于知识图谱的多跳推荐与音乐脉络可视化；
4. 经正式授权的国内音乐播放 Provider；
5. 移动端原生播放器接入；
6. 用户主动导入已有歌单；
7. 更精细的偏好模型与主动式赛程设计。
