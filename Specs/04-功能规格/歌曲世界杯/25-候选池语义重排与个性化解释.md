# 候选池语义重排与个性化解释

- 状态：草案
- 优先级：P0
- 依赖：`23-候选歌曲证据模型与质量控制.md`、`24-音乐偏好事件与长期记忆.md`、`03-技术架构/12-音乐探索Agent运行时与自主决策架构.md`

## 1. 目标

候选池 Agent 已能在线发现、核验并准备“赛事规模 × 2”的规范歌曲，但“数量足够”不等于“比赛值得玩”。本功能在不引入第三个业务 Agent 的前提下，让候选池生成 Agent 对已核验候选进行语义重排，明确区分主池与补位池，并给出具体、可读、可审计的入选解释。

本功能回答三个用户可见问题：

1. 为什么这首歌适合这次世界杯；
2. 为什么它进入主池，而不是作为补位；
3. 若它来自相近艺人扩展，扩展关系是什么。

## 2. 范围与非目标

### 本期范围

- 在 `CATALOG_IMPORTED` 且通过约束校验的候选中进行排序；
- 以用户当前输入为第一优先级，长期偏好事件仅作弱增强；
- 支持艺人、场景、情绪、流派、语言、年代、文化语境、歌词主题和创作背景等解释维度；
- 对 16 首与 32 首赛事分别返回等量主池和补位池；
- 使用可并行的 LLM 子任务生成排序建议和具体理由；
- 模型不可用、格式失效或超时后，仍返回可开赛的确定性降级结果。

### 非目标

- 不将 LLM 评分作为歌曲实体真实性依据；
- 不从模型记忆中补充歌曲、艺人、歌词或创作事实；
- 不向用户展示隐藏分数、思维链、系统提示词或内部工具参数；
- 不强制艺人比例，也不以“艺人数更多”作为质量标准；
- 不改变网络搜索、MusicBrainz 核验和 Java 入库作为候选发现主链路的定位。

## 3. 优先级与输入边界

```text
用户本次明确约束与偏好
  > 本次可引用的在线/目录/Milvus 证据
  > 用户近期音乐偏好事件（弱增强）
  > 通用音乐常识
```

- `ARTIST_LOCKED`：排序只能发生于允许艺人集合中；不因多样性降低任何作品优先级。
- `ARTIST_SEEDED`：用户点名艺人的作品和相近扩展作品都可参与；扩展作品必须标记与起点的关联。
- `OPEN_DISCOVERY`：Agent 依据当前输入自主判断哪些偏好信号更重要；不得用无关本地种子填充排序结果。
- 长期偏好只能打破相近候选之间的排序平局，不能覆盖用户本期明确表达的方向。

## 4. ReAct 决策与子任务

语义重排不是固定的“发现完成后必跑一步”。Supervisor 根据候选数量、证据密度、意图范围、已有解释质量、剩余时间与预算，自主决定是否调用 `rerank_candidates`、是否请求 Milvus 主题卡、是否调用并行排序子任务，或直接进入质量校验。

当 Supervisor 选择 `rerank_candidates` 时，可调用的技术子任务包括：

- `prepare_ranking_context`：压缩用户输入、意图策略、允许约束、偏好事件与每首候选的可信元数据；
- `score_candidate_batch`：对 12–20 首已核验候选形成结构化排序建议与理由草案；不同批次可并行执行；
- `merge_rankings`：合并批次结果、消除重复版本、应用约束，并选出主池和补位；
- `critique_explanations`：只检查理由是否具体、是否引用不存在的事实、是否违反艺人范围，不产出新的候选实体。

这些子任务是候选池 Agent 的内部工具，不是面向用户的第三个业务 Agent。运行时允许因为预算、已有高质量理由或依赖故障跳过其中任意一个；不得规定其固定调用顺序。

## 5. 排序与解释契约

### 5.1 输入

每首可排序候选至少提供：

```json
{
  "recordingId": "uuid",
  "title": "歌曲名",
  "artistName": "艺人",
  "albumTitle": "可为空",
  "catalogSource": "EXTERNAL_VERIFIED",
  "verificationStatus": "VERIFIED",
  "discoverySources": [],
  "evidenceSummary": [],
  "themeClaims": [],
  "originRelation": "SEED_ARTIST | ADJACENT_ARTIST | OPEN_DISCOVERY"
}
```

`themeClaims` 只可来自已审核的 Milvus 主题卡；`evidenceSummary` 只可来自已保存的公开来源。任何缺失字段必须被当作“未知”，不得由模型补写为事实。

### 5.2 输出

每首主池或补位歌曲新增以下逻辑字段：

```json
{
  "rankingReason": "与用户当前偏好直接相关的 30–100 字说明",
  "selectionFactors": [
    {"kind": "scene|mood|genre|artist_relation|culture|lyrics_theme|creation_context", "text": "可审计短说明"}
  ],
  "originRelation": "SEED_ARTIST",
  "originRelationText": "来自你点名艺人的已核验作品",
  "explanationStatus": "MODEL_GENERATED | CATALOG_FALLBACK"
}
```

- `rankingReason` 必须连接至少一个当前用户信号和至少一个可信候选事实或主题证据；
- `selectionFactors` 展示 1–3 条，避免把证据详情堆满候选卡；
- 主池和补位使用同一套解释契约，只在 `poolRole` 上不同；
- 解释中允许使用“可能更贴近”“适合作为比较对象”等推荐性表述，但不得把推测写成客观音乐事实。

## 6. 主池与补位决策

- 16 首赛事：前 16 首为 `MAIN`，后 16 首为 `RESERVE`；
- 32 首赛事：前 32 首为 `MAIN`，后 32 首为 `RESERVE`；
- 同一艺人/标题的重复版本先由既有版本去重逻辑处理；
- 用户明确锁定艺人时，主池/补位均不得越界；
- 用户允许扩展时，不设置硬性扩展比例；`originRelation` 只用于解释来源，不是配额；
- 前端移除某首主池歌曲后，按排序顺序直接补入首个 `RESERVE`，不重新调用模型。

## 7. 失败降级与质量门禁

如果排序模型超时、响应无法校验、批次结果缺失或 Critic 判定理由引用了无证据事实：

1. 丢弃无效模型输出，不影响已核验候选；
2. 以确定性规则保持约束、去重与主池/补位数量；
3. 使用 `CATALOG_FALLBACK` 解释，说明“基于已核验艺人/场景/语言等目录事实入池”，不得伪装成模型洞察；
4. 在运行轨迹记录降级原因，前端仅在必要时以简短提示显示“部分理由采用目录说明”。

以下情况必须阻断 `ready_for_confirmation`：正式位不足、出现未核验实体、违反 `ARTIST_LOCKED`、候选重复版本未处理。理由生成失败本身不阻断开赛。

## 8. 前端展示

候选确认页每张卡片展示：封面、歌名、艺人、主池/补位标签、`rankingReason` 和试听/平台搜索入口。

若 `originRelation` 为 `ADJACENT_ARTIST`，显示简洁的“相近方向扩展”标签；点击后展开 1–3 条 `selectionFactors` 与公开来源摘要。`SEED_ARTIST` 显示“从你的起点艺人延展”，`OPEN_DISCOVERY` 显示“由本次偏好发现”。不展示数值评分。

移动端默认只显示理由首段和一个来源标签，避免候选确认页过长；详情按需展开。

## 9. 验收标准

1. 输入“徐佳莹、艾怡良和郑宜农，适合深夜的华语创作女声”可返回 32+32 首，并为每首给出具体理由或明确的目录降级说明；
2. 输入“只玩张悬的歌曲世界杯”时，所有主池与补位均属于允许艺人，理由不引入外部艺人；
3. 输入“雨夜独处、克制但不阴郁的中文歌”时，理由能引用场景/情绪/语言或已审核主题卡，且不混入无关本地种子；
4. 模型单批次失败时，结果仍可创建赛事，且 `explanationStatus` 正确标为 `CATALOG_FALLBACK`；
5. 前端能区分主池、补位、起点艺人作品与相近方向扩展作品；
6. 不记录或输出 chain-of-thought、完整网页正文、内部地址、密钥与隐藏评分；
7. Agent、Java、Web 自动测试和一次真实 SSE 联调通过。
