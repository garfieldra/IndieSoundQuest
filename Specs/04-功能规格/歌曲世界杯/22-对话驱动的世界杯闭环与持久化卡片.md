# 对话驱动的世界杯闭环与持久化卡片

**状态：** 草案
**依赖：** `21-对话式音乐探索主入口与会话状态.md`、`03-技术架构/11-对话式会话运行时技术规格.md`

## 1. 目标

将歌曲世界杯恢复为产品最显性的主线，而不是普通音乐聊天后的文字建议。用户从一个主动、温和的开场问题进入：

> 我们的歌曲世界杯应该从哪开始？描述一下你的音乐喜好，或告诉我最近反复听的歌。

对话承担偏好澄清和候选方向构建；世界杯承担偏好采集；报告承担赛后解释与下一轮探索。整个过程在同一可恢复会话中连续发生。

## 2. 用户闭环

```text
SYSTEM_NOTE 开场引导
  → USER_TEXT 多轮偏好表达 / 补充 / 否定
  → AGENT_TEXT + 安全计划、进度
  → 必要时 CLARIFICATION_CARD
  → CANDIDATE_POOL_CARD（候选池已完成、等待确认）
  → 用户编辑、补位、确认
  → TOURNAMENT_CARD（赛事已创建、对话内逐场投票）
  → REPORT_CARD（报告生成中 / 已完成）
  → 报告详情与继续对话 / 下一场世界杯
```

所有箭头对应显式用户操作或已完成领域事实；Agent 不可静默创建赛事、替用户投票，或把未核验的网络线索直接写入卡片。

## 3. 卡片状态机与持久化

| 卡片 | 创建条件 | 持久化引用 | 可执行操作 |
| --- | --- | --- | --- |
| `SYSTEM_NOTE` | 新建空会话 | 无 | 开始输入 |
| `CLARIFICATION_CARD` | 具名艺人确有歧义 | mention + 候选 MusicBrainz 实体 | 选择实体、返回修改 |
| `CANDIDATE_POOL_CARD` | 候选 ReAct 已完成并经 Java 校验 | candidate run / recordingIds / size / 状态 | 查看、移除、补位、重新生成、确认开赛 |
| `TOURNAMENT_CARD` | 用户确认候选并成功创建赛事 | tournamentId | 进入赛事、查看当前进度、返回会话 |
| `REPORT_CARD` | 完赛后报告任务创建或完成 | tournamentId + reportId + status | 查看详情、重试、继续追问 |
| `RECOMMENDATION_CARD` | Agent 输出已校验推荐集合 | 规范歌曲/艺人 ID 或公开搜索链接 | 去平台搜索、基于此继续探索 |

`conversation_message` 必须完整映射并持久化 `type`、`card_type`、`card_payload_json`。卡片负载只保存展示快照及稳定引用；每次读取详情均回读 Java 领域事实，不能以旧消息 JSON 作为事实来源。

## 4. Agent 决策边界

- 音乐探索 Agent 使用 ReAct 自主判断：继续对话、请求澄清、开始候选检索，或在候选成功后交付候选池卡。
- “偏好是否足够”不是前端关键词规则。可由 Agent 综合明确艺人、风格、情绪、语言、反向约束和最近上下文判断。
- 若用户直接说“开始 32 首世界杯”，这是明确授权；Agent 可立即进入候选生成，但仍要先进行实体澄清并等待候选确认后创建赛事。
- 报告 Agent 仅在赛事完成后生成报告卡；报告完成后仍属于同一会话，用户可追问冠军、对局或推荐理由。

## 5. 接口增量

```text
POST /conversations/{id}/messages:stream
  → message_completed 中携带已持久化 cards[] 引用

POST /conversations/{id}/candidate-pools:stream
  → 显式由“构建候选池”或用户明确开赛触发

POST /conversations/{id}/candidate-pools/{poolId}/confirm
  → 创建 tournament，写 TOURNAMENT_CARD 与关联表

POST /conversations/{id}/tournaments/{tournamentId}/report:stream
  → 创建 / 更新 REPORT_CARD

POST /conversations/{id}/system-notes/tournament-completed
  → 赛事完成回流时写入 SYSTEM_NOTE，并刷新赛事卡
```

既有候选池、赛事、报告 API 保持兼容；新增会话 API 负责把这些领域操作转为可恢复卡片。

## 6. 前端体验

- 空会话不显示泛聊天欢迎语，改为世界杯导向的系统开场卡和两个低门槛示例。
- `CANDIDATE_POOL_CARD` 在对话中显示候选数量、候补数量、进度与“进入确认”按钮；编辑进入专用确认界面，不在聊天流塞 64 张封面。
- `TOURNAMENT_CARD` 是对话内赛事的稳定锚点。候选确认、逐场投票、完赛、生成报告和报告详情均在同一条时间线中完成；不得通过 hash、路由跳转或嵌入旧版 `App` 作为主流程。
- 为兼容历史 `CANDIDATE_POOL_CARD`，若旧负载仅含歌曲 ID 而缺少展示快照，卡片必须明确提示并提供“重新构建完整候选池”，不能显示 `0 / N` 后留下不可点击的开赛按钮。
- 当前执行过程只附着在当前 `AGENT_RUN` 下；完成后保留折叠摘要。
- `REPORT_CARD` 只显示冠军、状态、标签与详情入口，完整报告继续使用既有详情页 / 长图能力。

## 7. 验收

1. 新会话首屏出现世界杯导向系统提示；用户无需先理解产品结构。
2. “徐佳莹、艾怡良、郑宜农，做一场 32 首比赛”可在必要澄清后直接进入候选 ReAct，并出现持久化候选卡。
3. 刷新页面、切换会话、断线恢复后，候选、赛事、报告卡仍正确呈现且不重复创建领域对象。
4. 候选确认后，用户在同一对话卡片内完成每轮投票；页面 URL 不发生世界杯路由或 hash 跳转。
5. 完赛后卡片可直接生成并持久化 `REPORT_CARD`；报告详情可在卡片内展开。
6. 报告完成后，用户可以继续在当前会话追问，无需重述本期赛事偏好。
