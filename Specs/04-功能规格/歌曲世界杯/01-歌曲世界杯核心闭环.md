**状态：** 草案 v0.1

**所属功能域：** `04-功能规格/歌曲世界杯/`  
**关联规格：** `01-产品/03-MVP产品规格：歌曲世界杯与音乐探索.md`、`03-技术架构/06-Java业务服务规格.md`、`03-技术架构/08-Web前端规格.md`

## 1. 目标与交付边界

本功能是 IndieSoundQuest 的第一个可运行纵向切片：未登录用户可从本地种子艺人发起一场 16 或 32 首的私有歌曲世界杯，完成所有二选一对局，并在刷新页面后继续赛事、查看冠军和晋级图。

本次交付只验证赛事领域的正确性与前后端联通，不依赖 Agent、Milvus、MusicBrainz、Apple Music 或真实音频播放。首个 UI 仅提供“单艺人 + 代表作”创建入口，但底层赛事模型从一开始保留 Agent 策展和赛后报告所需字段。

### 1.1 本次必须交付

```text
选择种子艺人 → 选择 16 / 32 首 → 创建草稿 → 确认赛程
→ 查看当前对局 → 投票并推进 → 完成决赛 → 查看结果
```

- 首个切片只开放 `POPULAR` 候选来源；`CUSTOM`、`RANDOM` 与 `AGENT_GENERATED` 作为后续可扩展来源，不把它们建模为不同赛事类型；
- 仅支持 16 / 32 首单败淘汰赛；
- Java 服务以 MySQL 为唯一业务事实源；
- React 可创建、继续、投票和查看结果；
- 每场赛事绑定当前访客，默认私有；
- 服务重启或浏览器刷新后，赛事和投票仍可恢复。

### 1.2 明确不做

- 艺人全文搜索、随机/自选候选池编辑；
- 登录账户、跨设备同步、历史列表和删除功能；
- 试听、外部播放链接、完整 Provider 同步；
- Agent 跨艺人策展、投票理由、赛后 Agent 洞察和偏好报告；
- 社交、公开排名、分享和评论。

这些能力保留接口扩展位置，但不得阻塞本功能闭环。

## 2. 用户可见行为

### 2.1 创建页

1. 页面通过 `GET /api/v1/artists` 加载本地种子艺人；
2. 用户选定一位艺人和赛事规模（16 或 32）；
3. 前端调用创建接口，服务端依据该艺人的种子代表作生成候选；
4. 页面展示候选歌曲和“生成赛程”按钮；
5. 确认后进入对局页。

首版不提供候选编辑。候选来源在 UI 明确标注为“代表作”，避免让用户误以为它是平台热度排行。

### 2.2 对局页

- 显示当前轮次、已完成票数、两首歌的封面、歌曲名/艺人/专辑名（可空）/版本标签；
- 用户点击任一“选择这首”后，按钮立即禁用；
- 投票成功后，从服务端返回的新赛事状态中渲染下一场待投对局；
- 无待投对局但赛事已完成时，自动进入结果页；
- 刷新页面时重新拉取赛事详情，恢复当前待投对局；
- 用户可离开页面，赛事不自动中止。

### 2.3 结果页

- 显示冠军、前四名和完整单败晋级图；
- 显示本场规模、完成票数与完成时间；
- 只描述“本场冠军”，不输出任何偏好或人格结论。

## 3. 领域规则

### 3.1 状态

```text
DRAFT --PATCH status=READY--> READY --first successful vote--> IN_PROGRESS --final vote--> COMPLETED
```

- `DRAFT`：已生成候选，但可在未来扩展为可编辑；本次只读展示；
- `READY`：赛程固定，尚无投票；
- `IN_PROGRESS`：至少一场对局已完成；
- `COMPLETED`：决赛完成，冠军写入；
- 不在本次提供中止或删除入口。

### 3.2 赛程

- 16 首预创建 15 场对局，32 首预创建 31 场对局；
- 每条 `TournamentEntry` 对应一个不同的 `Recording`；
- 使用创建时持久化的 `bracket_seed` 将候选打乱，保证同一赛事可复现；
- 全部 Match 在将赛事更新为 `READY` 时预创建；首轮填入双方 Entry，后续轮次初始为空；
- 上游对局结束后，胜者写入唯一确定的下游槽位；
- 任意赛事在任意时刻最多存在一个“双方均已就绪且未完成”的当前对局；
- 不支持平票、撤票或修改投票结果。

### 3.3 投票一致性

`POST /tournament-matches/{matchId}/votes` 必须在一个数据库事务中完成：

1. 确认当前访客拥有赛事；
2. 确认 Match 是双方 Entry 均已就绪的 `PENDING` 对局；
3. 确认 `selectedEntryId` 是该对局的一方；
4. 对 Match 使用乐观锁；
5. 创建唯一 Vote、写入胜者、更新 Match 状态；
6. 把胜者写入下一场的指定槽位；
7. 首票将赛事从 `READY` 改为 `IN_PROGRESS`；
8. 决赛投票时在同一事务写入冠军、`COMPLETED` 与 `completed_at`；
9. 返回更新后的赛事摘要和下一场待投对局。

请求必须带 `Idempotency-Key`。相同键重试返回首次成功结果；不同键重复投同一 Match 返回 `MATCH_ALREADY_COMPLETED`，不得生成第二票。

## 4. 数据与持久化设计

本功能确定使用 **Spring Data JPA + Flyway**。Flyway 管理可重复执行的 MySQL Schema 与种子数据；JPA 负责赛事聚合的读写。

### 4.1 初始表

| 表 | 核心字段/约束 | 用途 |
| --- | --- | --- |
| `guest_session` | `id` UUID、`token_hash` 唯一、`created_at` | 匿名访客归属；浏览器只持有 HttpOnly Cookie 原始 token |
| `artist` | `id` UUID、`name`、`sort_name` | 本地种子艺人 |
| `recording` | `id` UUID、`artist_id`、`title`、`album_title` 可空、`version_label` 可空、`seed_rank`、`cover_url` 可空、`cover_source`、`cover_status`、`cover_fetched_at` | 种子歌曲元数据与合规封面外链 |
| `tournament` | `id` UUID、`guest_session_id`、`artist_id` 可空、`candidate_source`、`exploration_brief` 可空、`agent_guidance_requested`、`size`、`status`、`bracket_seed`、`winner_entry_id`、`version` | 赛事根聚合 |
| `tournament_entry` | `id` UUID、`tournament_id`、`recording_id`、展示快照；`(tournament_id, recording_id)` 唯一 | 赛事候选与历史展示快照 |
| `tournament_match` | `id` UUID、`tournament_id`、`round_number`、`match_index`、双方/胜者 Entry、`next_match_id`、`next_slot`、`status`、`version`；`(tournament_id, round_number, match_index)` 唯一 | 对局和晋级关系 |
| `vote` | `id` UUID、`match_id` 唯一、`selected_entry_id`、`idempotency_key` 唯一、`created_at` | 单次有效投票与幂等结果 |

所有主键使用 UUID。MySQL 时间字段使用 UTC 的 `timestamp(3)`；枚举以字符串保存，避免序号耦合。

首个切片要求 `artist_id` 非空、`candidate_source=POPULAR`、`exploration_brief` 为空且 `agent_guidance_requested=false`；这属于接口校验，不应收窄数据库模型。后续跨艺人 Agent 策展赛事允许 `artist_id` 为空。

### 4.2 种子数据

- 使用一位可展示的中文艺人和至少 32 条不同 Recording；
- 写入歌曲名、艺人、可选专辑名、版本标签和合规封面外链；不写入歌词、封面二进制或音频；
- 数据源与版权说明沿用音乐数据规格；在本地开发环境中该数据只用于功能演示；
- `seed_rank` 明确代表演示候选顺序，不能称作真实平台热度。

## 5. HTTP API 契约

统一前缀为 `/api/v1`；所有响应 JSON 使用驼峰字段；错误沿用 Java 服务规格中的统一错误格式。

### 5.1 艺人和候选预览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/artists` | 列出可创建赛事的种子艺人 |
| `GET` | `/artists/{artistId}/recordings?size=16\|32` | 预览按 `seed_rank` 选出的代表作 |

### 5.2 创建与确认赛事

| 方法 | 路径 | 请求/行为 |
| --- | --- | --- |
| `POST` | `/tournaments` | 请求 `{ "artistId": "uuid", "size": 16, "candidateSource": "POPULAR", "agentGuidanceRequested": false }`；创建 `DRAFT` 与 Entry。当前仅接受 `POPULAR` 与 `false` |
| `PATCH` | `/tournaments/{tournamentId}` | 请求 `{ "status": "READY" }`，校验候选、生成完整赛程并进入 `READY`；已是 `READY` 时返回当前状态 |
| `GET` | `/tournaments/{tournamentId}` | 返回赛事、Entry、全部 Match、当前待投对局、结果摘要 |

`POST /tournaments` 响应至少包含：

```json
{
  "id": "uuid",
  "status": "DRAFT",
  "size": 16,
  "artist": {"id": "uuid", "name": "五月天"},
  "entries": [{"id": "uuid", "title": "...", "artistName": "五月天"}]
}
```

### 5.3 投票

```http
POST /api/v1/tournament-matches/{matchId}/votes
Idempotency-Key: 018f...
Content-Type: application/json

{"selectedEntryId": "uuid"}
```

成功响应：

```json
{
  "tournamentId": "uuid",
  "tournamentStatus": "IN_PROGRESS",
  "completedVoteCount": 1,
  "currentMatch": {
    "id": "uuid",
    "roundNumber": 1,
    "leftEntry": {"id": "uuid", "title": "..."},
    "rightEntry": {"id": "uuid", "title": "..."}
  },
  "winner": null
}
```

决赛完成时 `tournamentStatus` 为 `COMPLETED`、`currentMatch` 为 `null`，并返回 `winner`。

### 5.4 必备错误码

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `TOURNAMENT_SIZE_INVALID` | 规模不是 16 / 32 |
| 400 | `TOURNAMENT_STATUS_INVALID` | 状态不允许当前操作 |
| 400 | `VOTE_SELECTION_INVALID` | 选择的 Entry 不属于该 Match |
| 403 | `TOURNAMENT_ACCESS_DENIED` | 非赛事所有者 |
| 404 | `ARTIST_NOT_FOUND` / `TOURNAMENT_NOT_FOUND` / `MATCH_NOT_FOUND` | 资源不存在或对调用者不可见 |
| 409 | `MATCH_ALREADY_COMPLETED` | 不同幂等键重复投票 |

## 6. 身份与权限

- 首次命中 `/api/v1/**` 时，`GuestIdentityFilter` 创建随机访客 token，服务端仅保存哈希；
- 原始 token 写入 `HttpOnly`、`SameSite=Lax` Cookie；前端不读取该值；
- 所有赛事、对局访问均按当前 Cookie 对应的 `guest_session_id` 过滤；
- 404 与 403 对外保持不泄露资源存在性的表现，前端统一展示“赛事不可访问”。

## 7. 前端实现范围

本功能先使用 React 基础组件与 `fetch` 封装；TanStack Query、Zustand、Ant Design 在后续前端依赖安装时引入，不能为了它们延迟首条链路。

建议最小路由：

| 路由 | 页面 |
| --- | --- |
| `/` | 种子艺人选择与赛事规模选择 |
| `/tournaments/:id` | 候选确认、当前对局、简化赛程 |
| `/tournaments/:id/result` | 冠军、前四、完整赛程 |

前端投票规则：每次投票创建 UUID 幂等键；网络错误时对同一 Match 重试必须复用该键；成功或终态冲突后才清除该键。

## 8. 测试与验收

### 8.1 Java 自动化测试

- 赛程生成：16/32 分别创建 15/31 场，轮次和下游槽位正确；
- 参数校验：规模错误、重复 Recording、缺少候选时创建/准备失败；
- 投票：胜者进入唯一确定的下一场；
- 决赛：冠军、完成时间与赛事状态原子更新；
- 幂等：同一 `Idempotency-Key` 两次调用只产生一条 Vote；
- 并发：两个不同键同时投同一 Match，至多一个成功；
- 权限：另一访客无法读取或投票；
- Flyway：空 MySQL 可迁移并加载种子数据。

### 8.2 端到端验收

- [ ] 用户能创建 16 首赛事，完成 15 次投票并得到正确冠军；
- [ ] 用户能创建 32 首赛事，完成 31 次投票并得到正确冠军；
- [ ] 赛事进行中刷新浏览器，仍展示同一场当前待投对局；
- [ ] 双击或网络重试不产生重复 Vote；
- [ ] 结果页前四和赛程路径正确；
- [ ] 无外部音乐接口、Agent 服务或媒体资源时，功能仍完整可演示；
- [ ] 页面不出现任何公开排行或社交入口。

## 9. 实施顺序

1. 在 Java 服务加入 Spring Data JPA、Flyway、MySQL 驱动、springdoc-openapi 与 Testcontainers 依赖；
2. 编写迁移、种子数据、枚举与实体；
3. 实现赛程生成器及其单元测试；
4. 实现访客身份、赛事创建/准备/查询/投票 REST 接口；
5. 使用 JUnit 5 + Testcontainers MySQL 运行集成测试，并在开发环境验证 Swagger UI；
6. React 实现创建、对局、结果三个页面并接入接口；
7. 以 Docker Compose 运行并完成 16 与 32 首人工验收；
8. 将实现状态更新为“已验证”，并在此文档记录接口偏差。
