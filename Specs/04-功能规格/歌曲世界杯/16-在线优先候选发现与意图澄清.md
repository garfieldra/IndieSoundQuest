# 在线优先候选发现与意图澄清

> 状态：已实现，待真实外部服务联调  
> 优先级：P0  
> 依赖：`14-候选歌曲Agent证据驱动探索与质量闸门.md`

## 1. 背景与目标

IndieSoundQuest 不能假定本地歌曲目录覆盖用户兴趣。候选池 Agent 的默认工作应是：理解用户输入 → 澄清不确定实体 → 从公开网络发现候选方向 → 用 MusicBrainz 核验歌曲与艺人 → 写入 Java 规范目录 → 生成可确认的 16/32 首赛事池及等量补位池。

本地目录的职责调整为已核验作品的缓存、去重来源和赛事稳定引用；它可加速命中，但不得成为发现范围的上限或首要前提。

## 2. 优先级约束

1. **意图澄清先于候选生成。** 输入中出现 `Asen` 这类可能对应多个艺人、拼写不完整或别名不唯一的实体时，Agent 必须返回澄清问题，不能静默猜测。
2. **在线发现先于本地补充。** 无论本地目录是否命中，开放探索与艺人起点模式都应优先尝试在线发现；本地结果可作为已核验补充。
3. **所有开赛候选必须规范化。** 网页仅产生带证据的发现线索；只有经 MusicBrainz 对齐并在 Java 目录获得 `recordingId` 的作品可进入赛事或补位池。
4. **持续补足而非单轮导入。** 直到达到 `size × 2`（16 首赛事为 32 首总池；32 首赛事为 64 首总池）、预算耗尽或证据确实不足，Agent 都可继续进行新的发现与核验批次。

## 3. ReAct 行动模型

候选池 Agent 的动作白名单扩展为：

```text
understand_preference
resolve_named_entities
request_clarification
plan_external_queries
search_web
extract_discovery_hints
resolve_musicbrainz_batch
search_catalog
rerank_candidates
submit_candidates
finish_insufficient
```

这不是固定顺序：Supervisor 根据黑板中的实体置信度、已核验数、各批次收益、网络质量、用户的锁定/开放意图和预算自主选择下一项动作。运行时只阻止无收益重复、超预算和未澄清实体后的静默生成。

### 3.1 实体澄清

- Java 通过 MusicBrainz 的艺人搜索返回候选实体：名称、别名、国家/地区、类型、存续期、disambiguation、MBID。
- 若精确名称只对应一个高置信实体，可自动确认并在界面显示“已识别”。
- 若多个实体接近、没有高置信命中或名称疑似拼写/译名，返回 `needs_clarification`，包含原始片段与候选项；此时阻塞整次生成，用户可选择一个或手动修正文本。只有确有歧义才触发澄清，不把低风险的唯一高置信命中变成额外交互。
- 候选项数量按实际歧义结果完整展示：少于 3 项不补齐，多于 3 项不硬截断；界面同时提供“以上都不是”的自由文本修正入口。
- 用户明确输入“只要 / 仅限 / 某艺人的歌曲世界杯”时，澄清后的实体成为 `ARTIST_LOCKED` 边界；否则作为探索起点，允许向外扩展。

### 3.2 在线发现与批量核验

- 每一轮由 Agent 规划至多 5 条查询，覆盖：指定艺人的代表作/深度曲目、相似艺人/风格、用户给出的语言/年代/场景；每条查询可获得至多 5 条公开结果。
- Tavily 资料必须包含可观察到的歌曲名与艺人名；必要时抓取受限的公开正文摘录增强证据。
- 每批最多提交 16 条强证据线索给 MusicBrainz；默认最多运行 5 轮。若仍低于目标，Agent 可基于失败原因重新规划查询并发起下一批，不能因“已调用过一次 MusicBrainz”停止。
- 每批保留来源 URL、证据片段、查询目的、MusicBrainz 对齐状态与拒绝原因，供候选确认页展示简洁依据。

## 4. API 与状态

候选池创建接口需要支持两类结果：

| 状态 | 含义 | 前端行为 |
| --- | --- | --- |
| `needs_clarification` | 存在待用户确认的具名实体 | 展示无歧义的选择项与“修正输入/忽略”操作；确认后继续同一请求 |
| `ready_for_confirmation` | 已达到开赛数与等量补位，或已明确补位不足 | 展示候选、来源与可移除后的补位机制；补位不足必须明确标识 |
| `insufficient_candidates` | 多轮在线发现与核验后仍不足开赛数 | 显示已核验结果、缺口和可继续扩展的输入建议 |

## 5. 验收场景

### 场景 A：混合艺人、目录无关

输入：`我喜欢 Asen、Kanye West、周杰伦、陶喆`。

- `Asen` 不应被静默绑定；必须在存在多义时请求确认。
- 确认后，即使本地目录没有上述任何歌曲，Agent 仍应发起在线发现与多批 MusicBrainz 核验。
- 对 32 首赛事，目标为 32 首 active + 32 首 reserve；只要公开资料与 MusicBrainz 可用，候选应主要来自本轮在线发现，而不是无关的本地缓存。
- 所有入选歌曲都有内部 `recordingId` 与可追溯发现/核验状态。

### 场景 B：单艺人锁定

输入：`我只想玩 Kanye West 的歌曲世界杯`。

- 先解析 Kanye West；只有确认成功后生成。
- 网络与 MusicBrainz 应持续补足该艺人的作品；不得因多样性规则引入其他艺人。

## 7. 已确认决策

1. 仅在确有必要时触发歧义澄清；一旦触发，阻塞整次候选生成，不能静默忽略歧义实体。
2. 候选项完整按实际数量展示，不硬凑、不硬截断；提供“以上都不是”的手动修正。
3. 未达到等量补位前不得进入确认页；只有补位完成或经过上限轮次后明确失败，才返回最终状态。
4. 最多 5 轮；每轮最多 5 条网络查询、每条至多 5 条结果、16 条 MusicBrainz 核验线索。运行时预算和超时需随之扩展。
