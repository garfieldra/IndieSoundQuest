# 对话式音乐探索主入口与会话状态

**状态：** 开发中
**适用范围：** 对话式 Web 主入口、音乐探索 Agent、赛后报告 Agent、歌曲世界杯嵌入式入口

## 1. 产品定位

IndieSoundQuest 的主形态从“功能页面集合”升级为持续的音乐探索对话：用户以自然语言开始、追问和修正，Agent 在对话中理解上下文、调用工具，并在恰当时机交付结构化卡片。

歌曲世界杯不再是首页唯一入口，而是 Agent 用于采集本期偏好的互动工具。用户可从一条对话消息中的赛事卡片进入沉浸式对阵页面；赛事结束后自动回到原会话，报告作为可打开的结果卡片出现。

首版仍只有两个业务 Agent：

- **音乐探索 Agent**：负责宽泛音乐问答、偏好澄清、候选歌曲发现、候选调整与赛事建议。
- **赛后报告 Agent**：负责读取已完成赛事事实，生成报告、解释选择轨迹、处理报告后的推荐与追问。

“会话运行时”仅负责访客归属、消息持久化、事件转发和把确定的领域事实传给上述 Agent；它不是第三个产品 Agent，也不得替 Agent 规定固定工具顺序。

## 2. 已确认的产品决策

| 维度 | 决策 |
| --- | --- |
| 首次入口 | 保留现有首页作为产品介绍与入口；点击“开始探索”进入对话 |
| 对话范围 | 宽泛音乐对话 + 开放式音乐探索，可问艺人、专辑、流派、创作背景与推荐 |
| 会话持久化 | 访客 Cookie 绑定多个可恢复会话，服务端持久化 |
| 会话列表 | 提供“最近探索”，支持新建、重命名、继续会话 |
| 记忆 | 同会话保留完整可用历史；跨会话只保存用户明确确认的长期偏好 |
| 主动性 | Agent 可以建议下一步，但不得自动创建候选池、赛事或修改用户偏好 |
| 世界杯入口 | 在对话中展示赛事卡片；点击进入独立沉浸式赛事页；完成后回流原会话 |
| 报告入口 | 对话中展示“报告已完成”卡片，点击打开独立完整报告详情页 |
| 卡片 | 候选池、歧义澄清、赛事、报告、推荐、计划/进度均为结构化消息卡片 |
| 上下文 | 最近消息原文 + 会话摘要 + Java 事实快照；Agent 可自主决定是否读取更深历史 |
| 赛事数量 | 单一会话可包含多场独立赛事，形成连续探索链 |
| 执行过程 | 计划与安全进度显示在当前 Agent 消息下方，默认可折叠 |

## 3. 体验闭环

```text
首页介绍
  → 开始探索
  → 对话会话（文本 + 安全执行过程 + 卡片）
  → 候选池确认卡
  → 赛事入口卡
  → 独立歌曲世界杯对阵页
  → 返回原会话
  → 报告完成卡
  → 独立报告详情 / 后续追问 / 下一场赛事
```

示例：

1. 用户：“我喜欢徐佳莹、艾怡良，但想找更冷一点、不要太摇滚的歌。”
2. 音乐探索 Agent 在必要时澄清“冷”的含义；否则直接进行网络发现、MusicBrainz 核验和候选建议。
3. 用户补充“多一点女性创作歌手”，Agent 保留本会话约束并调整候选卡，而不是要求用户重述所有偏好。
4. 用户确认后点击“用这 16 首开始歌曲世界杯”。
5. 赛事完成后，页面带 `conversationId` 返回；赛后报告 Agent 生成报告完成卡。
6. 用户点击详情，或在对话中继续问：“为什么推荐魏如萱？”

## 4. 消息与卡片模型

### 4.1 消息类型

```text
USER_TEXT             用户文本
AGENT_TEXT            经审查的 Agent 自然语言回复
AGENT_RUN             某次 Agent 运行的容器消息，内含计划/进度/最终卡片
CLARIFICATION_CARD    艺人或实体歧义确认
CANDIDATE_POOL_CARD   候选歌曲池与编辑入口
TOURNAMENT_CARD       赛事状态、进入/返回入口
REPORT_CARD           报告完成摘要与详情入口
RECOMMENDATION_CARD   歌曲、艺人与可外跳的平台搜索链接
SYSTEM_NOTE           非模型生成的会话提示，例如赛事已完成
```

`AGENT_TEXT` 与卡片可以同属一条 Agent 回合；卡片数据必须来自 Java 校验后的领域对象，而不能直接信任模型输出。

### 4.2 卡片行为

- 候选池卡支持查看、移除、恢复、补位、重新生成与“开始赛事”。
- 澄清卡只在实体确有歧义时阻塞候选生成；用户确认后续跑同一会话的探索回合。
- 赛事卡显示规模、当前进度、冠军（如已完成）与“进入赛事”。
- 报告卡显示冠军、版本、三个以内探索标签、生成时间和“查看完整报告”；不在对话流直接堆叠完整长报告。
- 推荐卡可展示歌曲/艺人、理由和“去平台搜索”；版权试听继续走既有 listening-options 能力。

## 5. 会话、记忆与事实边界

### 5.1 数据模型（Java / MySQL）

新增或演进以下持久化对象：

```text
conversation
  id, guest_session_id, title, summary, status, created_at, updated_at, last_message_at

conversation_message
  id, conversation_id, role, type, text_content, card_type, card_payload_json,
  agent_run_id, sequence_number, created_at

conversation_tournament_link
  conversation_id, tournament_id, relation_type, created_at

music_preference_memory
  id, guest_session_id, content, source_conversation_id, confirmation_status,
  superseded_at, created_at, updated_at
```

规则：

- `Tournament`、投票、候选歌曲、报告仍是已有领域表的唯一事实来源；消息中的卡片仅保存稳定引用与展示快照。
- `conversation_message.card_payload_json` 不存 Prompt、原始 CoT、工具原始返回、密钥或未净化网页正文。
- 跨会话记忆只有当用户明确说“记住”“以后都不要”“我长期喜欢”等，或在确认卡中主动保存时才写入 `music_preference_memory`。
- 用户可在会话设置中查看、删除或撤销长期偏好；首版不做账号体系，删除范围仅限当前访客 Cookie。

### 5.2 上下文装配

每次 Agent 回合按预算装配：

1. 当前用户消息与最近 N 条高相关原文；
2. 当前会话摘要；
3. 已确认的跨会话长期偏好；
4. Java 读取的当前候选池、关联赛事、报告和约束事实快照；
5. 仅在 Agent 判断必要时读取更早消息或调用网络、MusicBrainz、Milvus。

摘要是可再生的辅助记忆，不是事实真相；涉及赛事、歌曲身份、投票结果的内容必须回读 Java 领域事实。

## 6. Agent 路由与能力边界

### 6.1 路由原则

- 对没有完成赛事事实的音乐问题、偏好探索、候选调整，由音乐探索 Agent 处理。
- 对已关联赛事的报告、冠军/对局解释、基于本期结果的推荐追问，由赛后报告 Agent 处理。
- 路由层只基于会话关联和用户显式目标选择可调用的业务 Agent；Agent 内部保持 ReAct 自主决定工具、子任务、顺序和停止条件。
- 宽泛音乐问答不强迫发起赛事。探索 Agent 可以回答后建议赛事，但必须等待用户确认。

### 6.2 共享工具与安全边界

- 音乐探索 Agent：网络搜索、MusicBrainz/Java 目录核验、Milvus 主题卡补充、候选池创建与调整。
- 赛后报告 Agent：赛事事实、网络搜索、Milvus 主题卡、已验证目录与推荐链接生成。
- 网络发现始终优先，MusicBrainz 负责歌曲身份核验；Milvus 只作为解释和推荐理由增强。
- 所有 Agent 为 ReAct 模式；计划、进度和工具摘要仅输出已白名单化的公开描述，绝不输出原始推理链。

## 7. API 与流式协议

### 7.1 会话 API

```text
POST   /api/v1/conversations
GET    /api/v1/conversations
GET    /api/v1/conversations/{conversationId}
PATCH  /api/v1/conversations/{conversationId}            # 重命名、归档
DELETE /api/v1/conversations/{conversationId}
POST   /api/v1/conversations/{conversationId}/messages:stream
GET    /api/v1/conversations/{conversationId}/events     # 可选断线恢复
```

`messages:stream` 接收 `content` 与可选的 `clientMessageId`。Java 先落用户消息，再调用对应 Agent；最终回复、卡片和关联引用经校验后持久化。

### 7.2 SSE 事件

```text
event: message_created
data: {"messageId":"...","role":"assistant","type":"agent_run"}

event: plan_updated
data: {"runId":"...","revision":2,"goal":"...","items":[...]}

event: progress
data: {"runId":"...","phase":"verify_musicbrainz","message":"正在核验歌曲身份"}

event: card_updated
data: {"messageId":"...","cardType":"candidate_pool","payload":{...}}

event: message_completed
data: {"messageId":"...","text":"我已经整理出…","cards":[...]}

event: error
data: {"code":"...","message":"用户可读说明","retryable":true}
```

事件必须可幂等，带 `messageId` / `runId` / revision。前端断线重连后以 REST 消息列表为准，避免重复插入卡片。生产代理继续为 SSE 路径禁用压缩与缓冲。

## 8. 前端信息架构

### 8.1 页面结构

```text
桌面：会话列表 | 对话时间线 | 可选的当前详情侧栏
移动：顶部会话标题 + 抽屉式最近探索 | 对话时间线
```

- 首页保留产品理念和“开始探索”；进入会话后不重复展示巨型首页标题。
- 当前输入框固定在时间线底部，支持发送、停止生成、重试。
- Agent 的计划和执行轨迹嵌入其当前消息气泡下方；结果出现后折叠，不遮挡前序消息或赛事详情。
- 赛事页通过路由携带 `conversationId` 与 `tournamentId`；完成、退出或返回时回到原会话，并刷新赛事卡。
- 报告详情页从报告卡打开，返回后保留原会话滚动位置。

### 8.2 会话列表与标题

- 新会话标题先使用用户第一句话截断生成；后续可由安全摘要自动更新，用户始终可手动重命名。
- 展示最近更新时间、关联赛事状态和当前报告状态；不显示模型内部标签。
- 支持新建、继续、归档/删除；删除会话不删除已明确保存的跨会话长期偏好，后者需单独删除。

## 9. 迁移策略

1. 新增会话与消息表、访客范围校验、会话 REST API，不改动现有赛事事实表。
2. 封装现有候选池 SSE 与报告 SSE 为会话消息事件，保留旧接口直到前端迁移完成。
3. 先交付“对话 → 候选池卡 → 赛事卡 → 独立赛事 → 回流会话”的闭环。
4. 再交付报告完成卡、报告详情跳转和报告后追问。
5. 最后接入跨会话长期偏好确认、会话摘要与会话列表管理。

首版不做：账号/复杂鉴权、多用户共享会话、社交消息、无限自动记忆、第三个业务 Agent、纯文本化世界杯投票。

## 10. 验收标准

- 用户可从首页进入新会话，发送宽泛音乐问题或探索偏好，并收到可追问的回复。
- 相同访客可恢复至少两个历史会话；不同访客不能读取彼此会话、赛事或记忆。
- 用户补充或否定偏好后，下一轮探索能引用当前会话约束，无需用户重复完整输入。
- 候选池、澄清、赛事、报告均以结构化卡片呈现，且每张卡片只引用 Java 校验后的事实。
- 一场 16/32 首赛事可从会话进入、完成后自动回到原会话；会话中可以存在多场赛事卡。
- 报告生成完成后出现报告卡；点击可打开完整报告详情，返回后可继续追问。
- 两个 Agent 的计划与进度在当前消息下流式呈现；网络中断不显示浏览器原始 `Load failed`。
- 不保存或展示原始 CoT、Prompt、密钥、内部地址、模型评分和未过滤网页全文。
