# 对话式会话运行时技术规格

**状态：** 开发中
**依赖：** `04-功能规格/歌曲世界杯/21-对话式音乐探索主入口与会话状态.md`
**适用范围：** Java 会话 API 与持久化、Python Agent 会话输入、React SSE 消费

## 1. 目标与非目标

本规格把既有“单次候选池运行”和“单次报告运行”接入可恢复的多轮会话，不改变歌曲世界杯、投票、报告的事实所有权。

目标：

- 访客可创建、恢复、删除多个会话；
- 每轮用户消息与安全的 Agent 最终消息/卡片可持久化；
- 前端通过一次 POST SSE 获得计划、进度、卡片更新与最终消息；
- 同一会话在后续轮次可使用受控上下文；
- 仅有音乐探索 Agent、赛后报告 Agent 两个业务 Agent。

非目标：账号体系、多人共享会话、跨设备迁移、原始 CoT 存储、通用自治路由 Agent、消息附件上传。

## 2. 组件职责

```text
React Conversation UI
  └─ Java Conversation API（访客权限、持久化、SSE、领域事实快照）
       ├─ MySQL（会话、消息、记忆、关联）
       ├─ Music Exploration Agent（Python / ReAct）
       └─ Tournament Report Agent（Python / ReAct）
```

### 2.1 Java

- 识别 `GuestSession`，所有会话查询强制带 `guest_session_id`。
- 先持久化用户消息与 `AGENT_RUN` 占位消息，生成单次 `agent_run_id`。
- 根据会话关联事实和用户目标选择一个既有业务 Agent；不调用 LLM 做“第三 Agent 路由”。
- 从赛事/报告/候选池领域表装配可验证事实快照；校验 Agent 回传的卡片引用。
- 将安全 SSE 原样/转译转发，最终把 `AGENT_TEXT`、卡片快照、摘要落库。

### 2.2 Python

- 音乐探索 Agent 承担宽泛音乐问答、偏好澄清、候选池生成与调整。
- 赛后报告 Agent 承担本期赛事解读、报告生成、报告后推荐与追问。
- 两者继续使用 LangGraph ReAct；可自主选择网络、MusicBrainz、目录、Milvus 与赛事事实工具。
- 不直接写 MySQL，也不信任/修改 Java 的赛事事实；只通过内部 Tool Adapter 读取或请求受限动作。

### 2.3 React

- 渲染持久化消息列表与结构化卡片。
- 一次只允许当前会话一个激活运行；新消息在运行中禁用或排队到首版后的能力。
- SSE 断开时以 `GET messages` 回读服务端事实，避免客户端猜测最终状态。

## 3. MySQL 数据模型与迁移

使用 Flyway 新增迁移，不修改既有 `tournament`、`tournament_match`、`tournament_preference_report` 的业务语义。

```sql
conversation (
  id BINARY(16) PK,
  guest_session_id BINARY(16) NOT NULL,
  title VARCHAR(120) NOT NULL,
  summary TEXT NULL,
  status VARCHAR(20) NOT NULL,           -- ACTIVE | ARCHIVED | DELETED
  last_message_at DATETIME(6) NOT NULL,
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  INDEX idx_conversation_guest_last (guest_session_id, status, last_message_at DESC)
)

conversation_message (
  id BINARY(16) PK,
  conversation_id BINARY(16) NOT NULL,
  client_message_id BINARY(16) NULL,
  agent_run_id BINARY(16) NULL,
  role VARCHAR(20) NOT NULL,             -- USER | ASSISTANT | SYSTEM
  type VARCHAR(40) NOT NULL,             -- USER_TEXT | AGENT_TEXT | AGENT_RUN | SYSTEM_NOTE
  text_content TEXT NULL,
  card_type VARCHAR(40) NULL,
  card_payload_json JSON NULL,
  status VARCHAR(20) NOT NULL,           -- COMPLETED | RUNNING | FAILED | CANCELLED
  sequence_number BIGINT NOT NULL,
  created_at DATETIME(6) NOT NULL,
  completed_at DATETIME(6) NULL,
  UNIQUE KEY uq_message_client (conversation_id, client_message_id),
  UNIQUE KEY uq_message_sequence (conversation_id, sequence_number),
  INDEX idx_message_conversation_sequence (conversation_id, sequence_number)
)

conversation_tournament_link (
  conversation_id BINARY(16) NOT NULL,
  tournament_id BINARY(16) NOT NULL,
  relation_type VARCHAR(30) NOT NULL,    -- STARTED | COMPLETED | REPORTED
  created_at DATETIME(6) NOT NULL,
  PRIMARY KEY (conversation_id, tournament_id)
)

music_preference_memory (
  id BINARY(16) PK,
  guest_session_id BINARY(16) NOT NULL,
  content VARCHAR(800) NOT NULL,
  source_conversation_id BINARY(16) NOT NULL,
  confirmation_status VARCHAR(20) NOT NULL,  -- CONFIRMED | REVOKED
  created_at DATETIME(6) NOT NULL,
  updated_at DATETIME(6) NOT NULL,
  revoked_at DATETIME(6) NULL,
  INDEX idx_memory_guest_status (guest_session_id, confirmation_status)
)
```

约束：

- `card_payload_json` 仅是展示快照，最少包括稳定 `tournamentId` / `reportId` / `recordingIds` 引用；读取详情时必须重新按访客权限读取事实表。
- `client_message_id` 来自前端 UUID，保证用户双击、网络重试不重复创建消息或 Agent 运行。
- `sequence_number` 由 Java 在事务内递增，前端据此排序；不使用客户端时间排序。
- 删除会话采用软删除；消息不返回给用户。长期偏好单独撤销，不随会话删除自动丢失。

## 4. REST API 契约

### 4.1 会话管理

```text
POST   /api/v1/conversations
GET    /api/v1/conversations?cursor=&limit=20
GET    /api/v1/conversations/{conversationId}
PATCH  /api/v1/conversations/{conversationId}       # title / archive
DELETE /api/v1/conversations/{conversationId}
GET    /api/v1/music-preference-memories
DELETE /api/v1/music-preference-memories/{memoryId}
```

`POST /conversations` 不启动 Agent，仅创建空会话。会话标题的默认值为“新的音乐探索”，收到首条用户消息后再用安全截断文本更新。

### 4.2 发送消息

```text
POST /api/v1/conversations/{conversationId}/messages:stream
Headers:
  Content-Type: application/json
  Idempotency-Key: <clientMessageId>

Body:
{
  "clientMessageId": "uuid",
  "content": "我喜欢徐佳莹、艾怡良，想听更冷一点的歌",
  "activeTournamentId": "uuid | null",
  "activeReportId": "uuid | null"
}
```

验证：内容 1–2,000 字；可选赛事/报告必须同时属于当前访客且已经关联当前会话。请求成功后 HTTP 保持 `text/event-stream`，不返回同步 JSON。

### 4.3 读取与恢复

```text
GET /api/v1/conversations/{conversationId}/messages?afterSequence=&limit=100
GET /api/v1/conversations/{conversationId}/active-run
```

断线恢复策略：客户端重新获取消息和 active-run；若 active-run 已 `COMPLETED`，直接渲染最终消息；若仍 `RUNNING`，重新连接同一 `agent_run_id` 的事件流或显示“仍在处理中”。首版不依赖浏览器保留的 SSE 缓冲。

## 5. SSE 事件与幂等

```text
event: message_created
data: {"messageId":"uuid","agentRunId":"uuid","sequenceNumber":18,"type":"AGENT_RUN"}

event: plan_updated
data: {"agentRunId":"uuid","revision":2,"goal":"...","items":[...]}

event: progress
data: {"agentRunId":"uuid","phase":"discover_web","message":"正在从公开音乐资料中寻找线索"}

event: card_updated
data: {"messageId":"uuid","cardType":"candidate_pool","payload":{"candidatePoolId":"..."}}

event: message_completed
data: {"messageId":"uuid","text":"我已整理出…","cards":[...]}

event: error
data: {"agentRunId":"uuid","code":"...","message":"用户可读错误","retryable":true}
```

规则：

- 同一 `agent_run_id + revision` 只可应用一次；消息最终以 GET 读回结果为准。
- `progress` 与 `plan_updated` 不持久化每一个中间版本；持久化最终安全摘要和最终卡片，避免消息表膨胀。
- Caddy 对消息流继续关闭压缩和缓冲，`flush_interval -1`；前端不得展示浏览器原始 `Load failed`。
- Java 运行超时、Agent 错误、网络断开都将 `AGENT_RUN` 标记为 `FAILED` 或保持 `RUNNING`，不能静默遗失用户消息。

## 6. 上下文装配契约

Java 向 Python 发出统一的 `ConversationAgentRequest`：

```json
{
  "requestId": "uuid",
  "agentRunId": "uuid",
  "conversation": {"id":"uuid", "summary":"...", "recentMessages":[...]},
  "confirmedMemories": [{"id":"uuid", "content":"..."}],
  "facts": {
    "activeCandidatePool": null,
    "linkedTournaments": [{"id":"uuid","status":"COMPLETED","champion":"..."}],
    "activeTournament": null,
    "activeReport": null
  },
  "userMessage": "...",
  "constraints": {"maxRecentMessages": 12, "maxHistoryMessages": 40}
}
```

上下文策略：

- Java 默认发送最近 12 条已完成文本消息、会话摘要、已确认记忆及关联事实摘要。
- 当 Agent 判断当前问题与更早消息强相关时，只能通过 `read_conversation_history` 工具按页请求同一会话的已过滤历史，最多再读取 28 条。
- Agent 永不获取其他访客会话、被撤销记忆、内部异常栈或原始网页正文。
- Java 在最终消息成功后异步请求“会话摘要建议”；摘要写入前需长度、敏感信息与事实引用校验。摘要失败不影响主回复。

## 7. 两个 Agent 的选择边界

路由规则是服务边界，不是第三个 Agent：

| 当前事实与用户目标 | 调用对象 |
| --- | --- |
| 宽泛音乐问题、风格/艺人/专辑探索、候选调整、要求开赛 | 音乐探索 Agent |
| 明确询问已完成赛事、报告、冠军、对局偏好、基于本场推荐 | 赛后报告 Agent |
| 用户在未完成赛事中询问“现在进展如何” | Java 直接读取赛事事实并回复系统消息 |
| 用户明确要求进入某张赛事/报告卡 | Java 返回/跳转已授权领域资源，不调用模型 |

选中业务 Agent 后，其内部仍为 ReAct：工具调用、是否搜索网络、是否查询 MusicBrainz、是否补充 Milvus、何时要求澄清均由它自行决定。不得为了会话形态改回固定的“先搜索、再核验、再生成”流水线。

## 8. 卡片校验与领域动作

- Agent 只返回 `card_intent` 与候选实体引用；Java 根据实际领域状态构造最终卡片。
- 创建候选池、开赛、投票、报告生成等写操作始终由用户点击卡片触发 REST 命令；Agent 只能建议，不能后台执行。
- 赛事完成事件由 Java 写入 `SYSTEM_NOTE` 和 `TOURNAMENT_CARD` 更新，并触发/提示报告生成；报告生成仍需用户主动点击或先前已确认的显式请求。
- 每个卡片动作携带 `conversationId`、`cardMessageId` 和幂等键，防止来自过期会话的重复操作。

## 9. 开发顺序

1. Flyway + JPA 实体/Repository + 访客隔离测试；
2. 会话 CRUD、消息列表、幂等用户消息与基础 React 时间线；
3. 把音乐探索 Agent 的 SSE 包装为 `messages:stream`，输出文本与候选池卡；
4. 将赛事卡与 `conversation_tournament_link` 接入现有开赛/完成回流；
5. 接入报告卡、报告详情和报告 Agent 后续追问；
6. 长期偏好确认/撤销、摘要压缩、断线恢复与压力测试。

## 10. 验收标准

- 同访客可以创建、列出、继续、软删除两个以上会话；跨访客请求返回 404/403 且不泄漏存在性。
- 相同 `clientMessageId` 重试不会新增第二条用户消息或第二次 Agent 运行。
- 发送消息后 1 秒内出现 `message_created` 或用户可读错误；每次成功运行均产生一个可恢复的最终 Assistant 消息。
- 候选池与报告卡只能引用当前访客拥有且当前会话已关联的事实资源。
- 断开 SSE 后刷新页面，可看到用户消息与最终结果，或看到可重连的运行状态。
- 在一段会话中，用户补充“不要太摇滚”后，下一轮候选生成会带上该会话约束；除非用户明确确认，不写入跨会话记忆。
- 代码与日志中不存在 Prompt、原始 CoT、密钥、其他会话内容或未经净化的网页全文。
