# 对话澄清与分层记忆运行时规格

## 1. 目标

统一音乐探索 Agent 必须能在多轮对话中保留语境，并且只在关键信息确实影响结果时暂停请求澄清。澄清不是一条普通回复，而是可持久化、可恢复的 Agent Run 中断点；记忆不是单一的“用户画像”，而是按时间尺度分层的运行时上下文。

## 2. 记忆分层

### 2.1 短期记忆

- 唯一事实源为 Java 持久化的 `conversation_message`。
- 每轮向 Agent 注入 `summary_through_sequence` 之后的全部未压缩文本消息，以及最近 3 张可展示业务卡片。未达阈值时不得固定截取 12 条，否则会导致离开窗口但尚未进入摘要的消息丢失。
- 原始消息保持角色、顺序和原文，不由模型覆盖；当前用户消息优先级最高。
- 推荐卡、报告卡等结构化事实作为独立上下文，不压缩成未经校验的自然语言事实。

### 2.2 中期记忆

- 使用 `conversation.summary` 保存滚动对话概要，最大 12000 字符。
- 中期记忆是“已离开近期窗口的旧对话压缩层”，不是每轮改写的用户画像。
- DeepSeek V4 Provider 的当前上下文上限按 1M 记录。应用不人为限制到 200K，但为系统提示、工具结果和模型输出预留约 15%，估算上下文达到 850K Token 时触发紧急压缩。
- 常规自动压缩固定在 20 轮用户对话时触发。“一轮”以一条用户消息计数，澄清回答也属于新的一轮。
- 压缩时保留最近 6 轮用户消息及其间的助手回答原文，位于需求指定的 5–8 轮区间中点；其余符合条件的旧段一次性增量压缩。
- 每次成功压缩后更新 `summary_version`、`summary_through_sequence` 与 `summary_updated_at`，不得反复总结同一段消息。
- 用户可以通过输入框旁的按钮手动提前触发增量压缩；压缩期间按钮应显示运行状态并禁止重复提交。
- 前端以估算 Token 占用显示记忆进度，但不暴露 Provider、ReAct 等内部实现术语；20 轮常规整理规则仍在后端独立执行。
- 摘要只保留：当前目标、已明确偏好、排除项、已确认实体、未解决问题、最近探索方向与重要结论。
- 摘要不得包含密钥、Cookie、内部地址、思维链或未展示的工具原始响应。
- 模型不可用时采用有界降级摘要，保证旧摘要不会丢失且不会无限增长。

### 2.3 上下文优先级

`当前消息/澄清答案 > 近期原始消息 > 近期持久化卡片 > 中期摘要 > 已确认长期偏好 > 历史反馈`。

当不同层冲突时，较新的原始表达覆盖旧摘要；长期偏好只能作为补充，不能覆盖本轮意图和本场赛事事实。

## 3. 澄清策略

Agent 可自主选择 `clarify`，但必须满足以下至少一项：

1. 同名艺人或实体歧义会改变检索范围；
2. 用户给出的约束互相冲突，无法安全执行；
3. 缺失的信息会显著改变结果，且无法通过公开检索可靠补齐。

可纠正的偏好强弱、推荐数量等细节不应阻塞。Agent 应提出一个最小问题，可给出实际数量的选项，也必须允许自由文本回答。

## 4. 可恢复工作流

1. ReAct Supervisor 决定 `clarify` 并返回 `CLARIFICATION_CARD / GENERAL_CLARIFICATION`。
2. Worker 不完成 Run，而是将原始 Agent 请求、澄清问题及恢复类型提交给 Java。
3. Java 持久化卡片和上下文快照，将 Run 标记为 `WAITING_FOR_USER`。
4. 用户在卡片中选择或输入答案，前端提交到同一 Run 的 `/answers`。
5. Java 将答案与原始请求合并，恢复同一 Run；Agent 重新自主决策，不进入硬编码工具顺序。
6. 成功后追加回答/卡片、更新中期摘要并将 Run 标记完成。

候选池的艺人身份澄清继续使用同一协议，但恢复类型为 `ARTIST_IDENTITY`。

## 5. 验收标准

- 普通对话产生必要澄清时，刷新页面后澄清卡仍存在且可继续。
- 回答澄清后复用原 `runId`，能够继续搜索、推荐、候选池或普通回答。
- 第 20 轮完成后触发压缩，压缩后保留最近 6 轮原文，更早轮次的关键偏好能从中期摘要进入后续决策。
- 新消息与旧摘要冲突时，以新消息为准，并在本轮完成后改写摘要。
- 日志、SSE、摘要和卡片均不记录私密思维链或凭证。
- 未达阈值时完成新回合不应改变摘要版本；达到任一阈值后自动增量压缩。
- 手动压缩后摘要版本递增，覆盖序号只向前移动；手动压缩也应压缩所有可压缩旧段，但仍保留最近 6 轮原文，不得全量压掉近期语境。
