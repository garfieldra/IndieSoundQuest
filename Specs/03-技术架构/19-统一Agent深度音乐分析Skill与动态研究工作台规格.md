# 统一 Agent 深度音乐分析 Skill 与动态研究工作台规格

## 1. 文档状态

- 状态：第一阶段、第二阶段的安全页面精读/证据覆盖及条件式 Claim 语义核验已实现并通过自动化与真实模型验收；更细粒度 Credits/版本工具和第四阶段评测集继续迭代；
- 上游约束：`12-音乐探索Agent运行时与自主决策架构.md`、`17-对话澄清与分层记忆运行时规格.md`、`18-Agent自适应研究实体解析与偏好推理规格.md`；
- 适用范围：统一音乐探索 Agent 对歌曲、专辑、艺人、版本及作品关系进行解释、比较和深入分析的能力。

## 2. 背景与问题

当前统一 Agent 已能理解偏好、在线搜索、解析艺人实体并生成歌曲推荐，但需要论证的音乐问题仍容易进入普通 `respond` 回答。主要限制包括：

- 普通回答与深度分析共享同一低信息密度上下文和输出约束；
- Agent 只看到少量搜索摘要，无法围绕当前问题持续读取、核验和补足证据；
- 研究是否充分容易退化为来源数量判断，不能表达“关键问题是否得到支持”；
- 缺少对事实、作品观察、解释和个人化听感的明确边界；
- 缺少可修改的研究目标、证据缺口和候选结论工作记忆；
- 没有稳定的深度分析质量评测，无法判断提示词或工具改造是否真正提高分析质量。

仅扩大字数或在 Prompt 中要求“深入”不能稳定解决上述问题。本阶段应增加可由统一 Agent 按需加载的深度音乐分析能力，同时避免形成新的固定工作流或第三个对外 Agent。

## 3. 核心原则

1. **只有一个对外 Agent。** 深度音乐分析是统一 Agent 可加载的 Skill，不是新的业务 Agent。
2. **Skill 不是工作流。** Skill 提供分析方法、证据要求、工具说明和质量标准，不规定固定工具顺序。
3. **运行时保持最小循环。** LangGraph 目标形态为 `AgentNode → ToolNode → AgentNode`，另设必要澄清中断与最终输出出口。
4. **工具保持原子化。** Agent 自主选择、跳过、重复、并行或停止工具调用；不得把所有分析步骤封装为不可观察的固定流水线。
5. **结构约束工程边界，不约束思考顺序。** 工具参数、实体身份、来源和可持久化卡片必须结构化；分析角度和研究次序由 Agent 决定。
6. **深度来自论证，不来自篇幅。** 每个重要判断应尽量说明可观察现象、产生的效果及其与问题的关系。
7. **事实与解释分层。** 不把 Agent 的听感或文本解读冒充创作者意图和已证实事实。
8. **网络研究为主要外部信息来源。** MusicBrainz 负责身份核验，Milvus 主题卡只作歌词主题与既有材料补充，不能限制在线研究。

## 4. 能力触发与路由语义

统一 Agent 可以将当前目标标记为 `deep_music_analysis`，但该标记只表示加载 Skill 和调整回答预算，不映射到一条固定分析图。

典型触发请求包括：

- 为什么某首歌听起来压抑、亲密、疏离或具有空间感；
- 分析歌曲的歌词、编曲、演唱、制作或叙事；
- 比较两首歌、两个版本、两张专辑或艺人的不同阶段；
- 解释歌曲在专辑叙事、艺人生涯或文化语境中的位置；
- 追问上一轮结论“为什么”“具体体现在哪里”“还有其他解释吗”；
- 用户明确要求深入、细致、严谨或基于来源分析。

以下请求通常不必加载本 Skill：

- 单纯询问发行时间、专辑名称、词曲作者等事实；
- 普通歌曲推荐；
- 明确要求开始歌曲世界杯或生成候选池；
- 问题可以通过一条已核验事实直接回答。

是否加载 Skill 由 Agent 结合本轮消息、近期上下文和已有卡片自主判断。运行时护栏只防止普通事实问答误触发高成本研究，不用关键词规则替代模型决策。

## 5. 深度音乐分析 Skill

Skill 被加载后向 Agent 提供以下指导，而不是预定步骤：

- 先识别用户真正想解释的现象或关系；
- 只选择与问题有关的分析维度，不机械覆盖全部维度；
- 必要时区分录音室版、现场版、重制版、翻唱版等对象；
- 优先查找可以支持核心结论的资料，而非堆积重复转载；
- 将可验证事实、作品观察、解释与听者推断明确区分；
- 不确定时降低措辞强度、记录边界或继续研究；
- 资料冲突时保留冲突，不静默挑选方便的说法；
- 默认形成“现象 → 听觉或文本效果 → 情绪/叙事作用 → 与整体问题的关系”的论证链；
- 回答应自然组织，不强制套用固定标题模板；
- 只有出现高价值缺口时才继续调用工具，自主判断何时停止。

可选分析维度包括但不限于：

- 歌曲、艺人、专辑与版本身份；
- 段落、重复、推进、高潮、停顿与留白；
- 旋律走向、和声张力与解决；
- 速度、律动、重拍、节奏密度；
- 配器、音色、动态、声场与音色反差；
- 演唱距离感、咬字、气声、音域与情绪控制；
- 歌词叙事视角、意象、语义转折和重复表达；
- 制作、混音空间、失真、混响、声像与压缩感；
- 专辑语境、创作背景、采访、时代与地域；
- 同艺人作品、相近作品、不同版本或时期的横向比较。

## 6. 动态研究工作台

Agent Run 可维护一个 `MusicAnalysisWorkspace`。工作台是可变的运行时工作记忆，不是必须按顺序填满的表单。

建议字段：

```yaml
subject:
  entity_type: recording | release | artist | version_pair | comparison_set
  canonical_ids: []
  display_names: []
question: 用户当前真正需要回答的问题
working_thesis: 当前可被修订或删除的核心解释
selected_dimensions: []
observations: []
claims: []
open_questions: []
source_conflicts: []
uncertainties: []
possible_next_actions: []
research_budget:
  tool_rounds_used: 0
  elapsed_ms: 0
  source_reads: 0
revision: 1
```

运行要求：

- Agent 可以在任何一轮新增、删除或重排 `selectedDimensions`；
- 新证据可以推翻 `workingThesis`，修改时保留可展示的安全计划摘要，不展示隐藏思维链；
- `openQuestions` 表示当前答案真正缺失的证据，不是预定义检查清单；
- 工具返回的原始长文本不直接永久堆入消息历史，应提炼成带来源的观察或 Claim；
- 工作台默认只属于单次 Agent Run，最终可展示结论、引用和卡片才进入对话持久化层。

## 7. 证据 Claim 模型

重要结论以 `EvidenceClaim` 表示：

```yaml
id: claim-uuid
statement: 编曲刻意保持较低密度，使人声听起来更靠近听者
claim_type: FACT | OBSERVATION | INTERPRETATION | LISTENER_INFERENCE
subject_ids: []
dimension: arrangement
evidence_refs: []
confidence: high | medium | low
boundary: 无法获得分轨工程，因此只描述成品中可观察到的结果
status: supported | partial | conflicting | unsupported
```

类型定义：

- `FACT`：发行时间、专辑、词曲作者、制作人、采访原话等可从来源核验的事实；
- `OBSERVATION`：可从合法获得的文本、音频特征或明确资料中观察到的结构与现象；
- `INTERPRETATION`：Agent 对现象如何服务情绪、叙事或表达的解释；
- `LISTENER_INFERENCE`：可能因个人经历和听觉习惯而异的感受或个性化关联。

每条 `evidenceRef` 至少记录来源 URL、标题、Provider、抓取时间、支持的 Claim 以及必要的短摘要。多个转载不得被计算为多个独立证据。无法支持的重要 Claim 应删除、降级或明确标注边界。

## 8. 原子工具集合

首版优先复用现有工具并补充缺失能力：

- `resolve_music_entity`：解析歌曲、艺人、专辑和具体版本，返回规范 ID 与候选；
- `search_web`：按 Agent 自主生成的查询检索公开资料；
- `search_domestic_content`：检索知乎、豆瓣、B 站等已接入中文信源；
- `read_public_source`：在安全、超时和内容长度限制下读取选定页面，而不只依赖搜索摘要；
- `search_musicbrainz`：核验作品身份、发行关系和基础 Credits；
- `retrieve_theme_cards`：从 Milvus 获取歌词主题卡和已整理材料；
- `inspect_discography`：整理歌曲在专辑和艺人生涯中的上下文；
- `compare_music_entities`：对规范实体的元数据、资料与已支持 Claim 进行并列整理；
- `save_analysis_note`：把长工具结果压缩为带来源的观察或 Claim；
- `verify_claim_sources`：检查事实 Claim 是否有来源、链接是否对应、来源之间是否冲突。

工具可以串行或并行调用。并行只用于彼此独立的研究问题；同一来源的后续读取、实体解析后的查询等存在依赖的动作必须等待上一步观察。

不得创建一个内部固定执行“规划、搜索、写作、审校”的黑盒 `deepAnalyzeSong()`。如需封装，只能封装单一职责的批量读取、去重或核验操作。

## 9. 自适应研究与停止条件

每轮工具返回后，Agent 根据工作台自主选择继续研究、修改论点、请求澄清或回答。判断依据包括：

- 用户的核心问题是否已得到直接回答；
- 当前核心 Claim 是否有足够支持；
- 是否仍存在会改变结论的重要 `openQuestion`；
- 新一轮搜索预期能否带来不同类型的证据；
- 当前来源是否只是重复转载；
- 是否接近工具轮数、总耗时、Provider 限流或模型预算。

不得仅以来源数量判断研究完成。所谓“维度覆盖”只针对 Agent 为当前问题选择的关键维度，不要求歌词、编曲、背景等全部存在。

默认采用软预算而非固定轮数流程：普通解释应尽快结束；明确深度分析可获得更高工具与输出预算。达到预算时，Agent 应交付已有的可靠结论并说明缺口。只有检测到重复查询、无新增证据或硬预算耗尽时，运行时才强制终止循环。

## 10. 澄清策略

仅在以下情况创建可恢复澄清中断：

- 同名歌曲或艺人对应多个高置信实体，且不同选择会改变分析结果；
- 用户要求比较但缺少必要比较对象；
- 现场版、录音室版或翻唱版的差异是问题核心而版本不明确；
- 用户给出的前提彼此冲突，无法通过公开资料安全修正。

可以安全推断、能在回答中声明假设、或者不会实质改变结论的细节不得阻塞。澄清继续沿用现有 `WAITING_FOR_USER` 与同一 `runId` 恢复机制。

## 11. 回答策略

回答长度由问题复杂度、证据数量和用户要求动态决定，不设置产品级字符上限，也不得在传输 Schema 或后处理中截断正文。以下仅是常见信息密度参考，不是上下限：

- 简单解释：约 400–700 字；
- 单曲深入分析：约 1000–1800 字；
- 对比或专辑语境分析：约 1200–2200 字；
- 多轮追问：优先只展开用户追问的维度，避免重复上一轮全文。

“某首歌是一首什么样的歌”“如何理解这首作品”等自然描述性问题属于解释型分析请求，应加载本 Skill，不得在多轮检索后回落到普通短答。若条件式事实审校后的正文相较初稿出现破坏性缩短，统一 Agent 必须重新审校并保留有证据的分析深度；审校只能收窄越界事实，不能把研究成果压成摘要。

默认回答包含但不机械套用：

1. 对用户问题的核心判断；
2. 若干具有具体音乐或文本依据的论证段落；
3. 可核验事实和来源；
4. 不确定性、替代解释或证据边界；
5. 少量具有明确比较价值的延伸作品。

禁止只堆叠“治愈、氛围感、细腻、高级”等形容词。重要解释应尽量形成：

```text
可观察现象 → 听觉/文本效果 → 情绪或叙事作用 → 与核心问题的关系
```

## 12. 条件式质量检查

质量检查不是每次回答的固定节点。出现以下任一条件时，Agent 应考虑调用 `verify_claim_sources` 或执行一次同模型结构化复核：

- 深度分析或比较分析包含多个重要 Claim；
- 使用了采访、歌词、制作资料或具体创作者意图；
- 来源存在冲突；
- 主观解释占比较高；
- Agent 判断核心论点置信度不足；
- 用户明确要求严谨、引用或深入研究。

检查内容包括：

- 是否直接回答了用户的“为什么”；
- 是否存在只有形容词、没有依据的段落；
- 是否混淆事实、观察、解释和听者推断；
- 是否虚构歌词、采访、Credits、版本或制作信息；
- 是否遗漏足以改变核心结论的关键问题；
- 是否可以用更具体的对比参照提高解释力。

检查后由 Agent 自主选择继续搜索、修改、删除、降级 Claim 或直接说明边界。

## 13. 版权与能力边界

- 不自动抓取、持久化或展示受版权保护的完整歌词；
- 可以分析用户主动提供的合理短片段，或使用主题卡和公开资料进行概括；
- 搜索摘要不得被当作完整歌词或精确作品文本；
- 没有真实音频输入或可靠音频资料时，不声称精确识别 BPM、和弦、调性、某秒出现的乐器或混音参数；
- 仅凭成品听感得出的声音判断必须属于 `OBSERVATION` 或 `INTERPRETATION`，并标注能力边界；
- 后续如支持合法音频上传或试听片段，可使用 `librosa` 等提取节奏、动态、频谱和结构特征，但算法特征不能自动等同于艺术意义；
- API Key、Cookie、内部地址、完整 Prompt、隐藏思维链与未经整理的工具原文不得进入回答、SSE 或模型外部上下文。

## 14. 前端与 SSE

对话流中只展示安全、可验证的执行摘要：

- 已识别需要解释的核心问题；
- 当前选择的分析角度；
- 正在核验歌曲或版本身份；
- 正在查找创作背景、制作资料或比较对象；
- 新证据导致计划调整；
- 正在核对关键结论与来源。

右侧动态计划显示当前 `MusicAnalysisWorkspace` 的公开投影，而不是完整工作台和思维链。最终回答在对话中自然展示；来源、Claim 边界和延伸作品可以附加轻量 `MUSIC_ANALYSIS` 卡片，卡片不是阅读正文的前置条件。

## 15. 持久化与多轮上下文

- 对话正文、最终来源卡和用户可见分析卡正常持久化；
- 工作台中的草稿、失败查询和隐藏复核内容默认不持久化；
- 可持久化卡片应记录规范实体 ID、核心结论摘要、引用来源、Claim 类型和分析版本；
- 后续“具体体现在哪里”“换个角度”“和另一首比较”等追问必须继承上一轮分析卡、近期原文和中期摘要；
- 新证据推翻旧结论时创建新版本并明确修订，不静默覆盖已展示回答；
- 未经用户确认的推断不得直接固化为长期音乐偏好。

## 16. 评测体系

建立 30–50 条首版深度分析数据集，覆盖：

- 单曲情绪与表达分析；
- 歌词主题和叙事视角；
- 编曲、演唱与制作解释；
- 同艺人不同时期作品比较；
- 录音室版、现场版、翻唱版比较；
- 专辑和文化语境；
- 同名歌曲、艺人歧义与必要澄清；
- 资料不足、来源冲突与不可验证问题；
- 多轮追问“为什么”“具体在哪里”“是否还有另一种解释”。

核心指标：

- 对用户问题的直接回应程度；
- 具体性和论证链完整度；
- 关键分析维度的相关性，而非维度数量；
- 事实准确率与实体版本准确率；
- 重要事实 Claim 的来源支持率；
- 解释与听者推断的边界正确率；
- 无依据形容词密度与幻觉率；
- 澄清必要性和恢复成功率；
- 工具调用轮数、重复查询率、P95 耗时与模型成本；
- 相比普通 `respond` 基线是否产生明显质量增量。

自动评分可以使用规则、来源一致性检查和 LLM Judge 组合，但必须保留一组人工标注的金标样例用于校准 Judge 偏差。

## 17. 分阶段实施

### 17.1 第一阶段：运行时与 Skill

- 注册 `deep_music_analysis` Skill；
- 增加深度分析语义目标与动态输出预算；
- 实现 `MusicAnalysisWorkspace` 和 `EvidenceClaim`；
- 将普通分析从固定短 `respond` 中解耦，但不新增对外 Agent。

### 17.2 第二阶段：原子研究工具

- 复用实体解析、网络搜索、国内信源、MusicBrainz 和 Milvus；
- 增加安全页面读取、Discography 上下文、比较整理和 Claim 核验工具；
- 允许 Agent 根据 `openQuestions` 自主生成查询和并行研究。

### 17.3 第三阶段：前端与多轮体验

- SSE 展示分析角度和计划修订；
- 持久化轻量分析卡和来源；
- 支持围绕上一轮 Claim 继续追问、比较或修订。

### 17.4 第四阶段：评测与优化

- 建立金标问题集和普通 `respond` 基线；
- 接入规则、来源核验和 LLM Judge；
- 根据失败样例优化 Skill、工具描述和停止条件，而不是硬编码样例流程。

### 17.5 后续阶段：合法音频分析

- 在存在合法音频输入和明确授权后增加音频特征工具；
- 将算法特征作为证据输入，不用算法输出替代 Agent 对语境和意义的解释。

## 18. 首版验收标准

1. 普通事实问题不会无故进入长研究；
2. 深度问题能够加载 Skill，并自主选择与问题相关的分析维度；
3. Agent 可以在工具结果后修改分析角度，而不是执行固定搜索顺序；
4. 回答至少包含一条完整的“现象 → 效果 → 作用 → 核心问题”论证链；
5. 重要事实 Claim 有可打开且与结论对应的来源；
6. 回答能区分事实、作品观察、解释和个人听感，不把解释冒充创作者意图；
7. 资料不足时主动降低结论强度或说明缺口，不虚构歌词、音频特征或采访；
8. 同名实体或版本歧义仅在确实影响结果时进入可恢复澄清；
9. 多轮追问继承上一轮分析对象、Claim 和来源，不从零开始；
10. 复杂分析可以触发条件式核验，简单回答不强制执行审校；
11. SSE 只展示安全计划与工具摘要，不泄露思维链；
12. 深度分析评测相较普通 `respond` 基线在具体性、论证链和来源支持率上取得明确提升。

## 19. 非目标

- 不新增第三个对外 Agent；
- 不建立固定的“计划—搜索—写作—审校”DAG；
- 不要求每次分析覆盖歌词、编曲、制作、背景等所有维度；
- 不把来源数量或回答字数直接等同于分析质量；
- 不在首版自动下载或分析版权状态不明的完整音频与歌词；
- 不将未经确认的音乐解读写入长期偏好档案；
- 不用本地 Milvus 覆盖范围决定某首歌是否可以被分析。
