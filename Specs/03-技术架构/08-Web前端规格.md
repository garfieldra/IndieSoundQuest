# Web 前端规格

**状态：** 草案 v0.1  
**最后更新：** 2026-08-01  
**上级规格：** `00-系统总体设计与规格路线图.md`  
**依赖规格：** `03-MVP产品规格：歌曲世界杯与音乐探索.md`、`06-Java业务服务规格.md`、`07-Python Agent服务规格.md`

## 1. 目标

前端为用户提供私有、轻量、以选择为中心的歌曲世界杯体验，并将 Agent 的赛前策展与赛后洞察呈现为可理解、可追溯的辅助信息。

前端不直接调用 MusicBrainz、Apple、LLM、Milvus 或 Python Agent 服务；所有业务与媒体 URL 均经 Java 业务服务获取。

## 2. 技术基线

| 类别 | 选型 | 用途 |
| --- | --- | --- |
| 框架 | React + TypeScript + Vite | 单页 Web 应用 |
| 路由 | React Router | 页面与受保护路由 |
| 服务端状态 | TanStack Query | API 请求、缓存、失效与重试 |
| 本地 UI 状态 | Zustand | 对局展示偏好、临时创建表单、SSE 状态 |
| 组件库 | Ant Design | 表单、反馈、模态框、可访问组件 |
| HTTP | fetch 封装 | Cookie、请求 ID、统一错误处理 |
| 图表/赛程 | 自定义 CSS Grid / SVG 组件 | 16/32 首单败赛程，不引入重型图编辑库 |
| 测试 | Vitest + React Testing Library + Playwright | 单元、组件与关键用户流程 |

## 3. 信息架构与路由

| 路由 | 页面 | 访问条件 |
| --- | --- | --- |
| `/` | 首页/创建入口 | 所有人 |
| `/artists/search` | 艺人搜索结果 | 所有人 |
| `/tournaments/new` | 经典赛事创建 | 所有人 |
| `/explore/new` | 探索赛事创建 | 所有人 |
| `/explore/drafts/:draftId` | Agent 候选草稿确认 | 当前草稿所有者 |
| `/tournaments/:tournamentId` | 对局与当前赛程 | 当前赛事所有者 |
| `/tournaments/:tournamentId/result` | 赛事结果与洞察 | 当前赛事所有者 |
| `/history` | 私人历史赛事 | 当前用户/访客 |
| `/taste-profile` | 整体音乐偏好报告 | 登录用户；访客展示登录引导 |
| `/settings/privacy` | 删除赛事与偏好数据 | 当前用户 |

未知赛事、无权访问或已删除赛事统一进入可理解的错误页，不展示其他用户数据是否存在。

## 4. 页面规格

### 4.1 首页

目标：帮助用户快速理解产品并创建第一场赛事。

必备内容：

- 一句话说明：“为喜欢的艺人办一场歌曲世界杯，发现自己的音乐偏好。”
- 艺人搜索框；
- 两个入口卡片：`经典世界杯`、`探索世界杯`；
- 进行中赛事入口（若有）；
- 最近完成赛事入口（若有）；
- 明确的隐私说明：赛事默认私有，不设公开排行。

不展示：全站热榜、其他用户活动、评论、社交关注或广告式推荐。

### 4.2 艺人搜索

行为：

1. 用户输入至少两个字符后，防抖请求 `GET /artists/search`；
2. 每个结果显示名称、别名/地区（可用时）、艺人图片占位或合规远程图片；
3. 用户选择后可进入经典或探索赛事创建；
4. 搜索无结果时提供重新输入提示，不让前端自行调用外部平台。

### 4.3 经典世界杯创建

表单字段：

| 字段 | 选项/规则 |
| --- | --- |
| 目标艺人 | 必填，来自规范艺人搜索结果 |
| 赛事规模 | 16 首或 32 首 |
| 候选来源 | 热门、随机、自选 |
| 候选歌曲 | 自选模式必须恰好选择赛事规模数量；其他模式可在确认前替换 |

用户确认后，前端调用 Java 创建草稿、保存候选、`prepare` 赛事，再跳转赛事页。任何失败必须保留当前表单选择，允许用户修正。

### 4.4 探索世界杯创建与候选草稿

用户填写：目标艺人、赛事规模、探索目标。

创建后：

1. 前端调用 `POST /exploration-tournaments/drafts`；
2. 获得 `requestId` 后，以 `EventSource` 订阅 `GET /agent-requests/{requestId}/events`；
3. 显示有限的用户可见阶段，例如“正在整理可用曲目”“正在查找可引用资料”；
4. `draft_ready` 后跳转草稿确认页；
5. 草稿页展示候选歌曲、覆盖说明、可用来源与警告；
6. 用户可替换或移除歌曲，但候选数量必须保持 16/32；
7. 用户确认后调用 `confirm`，生成不可变赛事并进入赛事页。

前端不得展示模型思维链、检索分数、完整网页内容或未审核的内部资料。

### 4.5 对局页

对局页是 MVP 的核心。它应让用户专注选择，不应变成聊天窗口。

布局：

```text
赛事标题 / 当前轮次 / 完成进度

左歌曲卡                 右歌曲卡
封面                      封面
歌名、艺人、专辑、版本      歌名、艺人、专辑、版本
试听 / 外部收听             试听 / 外部收听
“选择这首”                 “选择这首”

可选：本轮选择依据（旋律、节奏、氛围、人声、编曲、歌词感受、说不清）
赛程缩略图 / 退出并稍后继续
```

交互规则：

- 用户必须明确选一首后才能推进；
- 选择按钮点击后立刻禁用双侧按钮，显示提交状态，防止重复投票；
- 投票成功后展示短暂的晋级反馈，再加载下一场待投对局；
- 网络失败时不乐观进入下一场，显示“重新提交”且保留本轮选择；
- 试听 URL 缺失时显示外部收听链接或“暂无试听”，不能阻塞投票；
- 用户刷新/重新打开页面后，从服务端恢复当前待投对局；
- 页面只展示赛事所有者自己的选择，不展示任何公共统计或他人偏好。

可访问性：

- 两首歌曲卡应具有明确焦点顺序和键盘可操作的“选择这首”按钮；
- 封面具有有意义的替代文本；
- 投票成功、错误、轮次变化使用 ARIA live region 提示；
- 颜色不是晋级/失败状态的唯一表达手段。

### 4.6 赛程视图

`TournamentBracket` 使用 CSS Grid 按轮次排列 Match：

- 16 首显示：16 强、8 强、4 强、决赛；
- 32 首显示：32 强、16 强、8 强、4 强、决赛；
- 已完成对局显示胜者、落选歌曲与投票原因（若用户填写）；
- 未决对局显示“等待上一轮结果”；
- 当前待投对局突出，但不自动滚动造成用户迷失；
- 窄屏以按轮次折叠的列表形式展示，保证手机可用。

### 4.7 结果页

必备内容：

1. 冠军歌曲及封面；
2. 完整晋级图和前四名；
3. 本场候选池和用户选择记录；
4. 经典赛事：可选“生成本场音乐总结”按钮；
5. 探索赛事：赛后洞察加载状态、总结、推荐和警告；
6. 每条推荐的“为什么推荐”与来源/用户选择标识；
7. “再办一场”“查看历史”“查看整体偏好”的下一步入口。

赛后洞察 SSE 事件只显示进度和最终结果。若 Agent 失败，冠军和赛程仍完整展示，并提供重试总结按钮。

### 4.8 历史与偏好报告

**历史页**显示进行中、已完成和中止的私有赛事，可继续或删除。删除操作需二次确认，并说明该赛事将不再参与偏好报告。

**偏好报告页**：

- 未达到 3 场赛事和 20 次有效投票时，展示具体积累进度；
- 达标后可请求生成或查看最新报告；
- 报告必须展示覆盖赛事数、投票数、置信边界；
- 展示音乐偏好维度和 3–5 条可解释推荐；
- 默认不出现教育、职业或心理推断；单场报告可展示明确标为“娱乐性观察”的人格彩蛋，且只能基于本场音乐选择，不作确定性结论；
- 提供删除报告和跳转隐私设置入口。

## 5. 前端状态管理

### 5.1 服务端状态

TanStack Query 管理艺人搜索、Recording 列表、赛事、对局、洞察、历史和偏好报告。

- Query Key 必须包含资源 ID 与必要筛选参数；
- 投票成功后失效赛事、当前对局、赛程和历史相关 Query；
- Agent `result` 事件后失效对应草稿/洞察/报告 Query；
- 不在浏览器持久化用户赛事、投票或完整 Agent 结果；
- API 缓存仅做展示优化，Java 服务才是事实源。

### 5.2 本地状态

Zustand 仅保存可安全丢失的界面状态：

```text
当前创建表单草稿
当前对局已选择但尚未提交的投票理由
SSE 连接状态与最后用户可见阶段
赛程视图的展开/折叠状态
```

不得在 Zustand/localStorage 保存访问令牌、访客 Cookie、用户完整偏好报告或受限媒体 URL。

## 6. API 客户端与错误处理

`apiClient` 必须：

- 使用 `credentials: 'include'`，让 Java 管理安全 Cookie；
- 对每个可变更请求生成 `X-Request-Id`；
- 投票请求生成并复用 `Idempotency-Key`，直到得到终态响应；
- 解析 Java 的统一错误格式并映射为用户可读提示；
- 对 `401/403` 跳转到合适身份提示，不暴露资源存在性；
- 对 `409` 刷新赛事状态并提示“该对局已完成”；
- 不直接重试投票等写请求；读取请求可由 TanStack Query 进行有限重试。

## 8. 视觉与内容原则

1. 移动端优先，桌面端展示完整赛程；
2. 比赛页面信息简洁，避免在投票时长篇解释或 AI 聊天气泡；
3. Agent 文案使用“根据本场选择”“在已完成赛事中”等限定语；
4. 所有关键事实提供来源入口，来源链接在新标签页打开；
5. 封面不可用时使用统一占位设计，不能显示破图；
6. 不在封面上叠加项目 Logo 或改造受限 Provider 视觉资产；
7. 全站不出现社交排名、用户昵称榜、评论或对外公开个人偏好。

## 9. 安全与隐私

- 用户身份由 HttpOnly Cookie 管理，React 不读取或保存 Token；
- 渲染 Agent/网页摘要时作为纯文本，禁止 `dangerouslySetInnerHTML`；
- 所有外链使用 `rel="noreferrer noopener"`；
- 删除确认明确说明影响赛事、洞察和聚合偏好；
- 访客模式不承诺跨浏览器保存，页面必须提前说明；
- 前端埋点只记录匿名页面/流程事件，不记录歌曲选择详情或完整报告文本。

## 10. 测试策略

### 10.1 单元与组件测试

- 16/32 候选数量、去重与版本标签展示；
- `MatchVotingPanel` 按钮禁用、失败重试和重复点击；
- `TournamentBracket` 在各轮次下的胜者推进展示；
- Agent 事件到 UI 阶段/警告/终态映射；
- 偏好报告的门槛、置信提示与敏感推断文案过滤；
- 无试听、无封面、无来源的降级 UI。

### 10.2 E2E 测试

1. 创建 16 首经典赛事 → 投完 15 场 → 查看冠军与赛程；
2. 创建 32 首探索赛事 → 接收候选草稿 → 调整后确认 → 完赛；
3. 投票请求网络重试 → 不出现重复 UI 成功态；
4. 刷新进行中赛事 → 恢复到正确待投对局；
5. Agent 洞察失败 → 赛程仍可正常查看和重试；
6. 删除赛事 → 历史和偏好报告状态更新；
7. 无权访问赛事 → 不泄露赛事信息。

## 11. 验收标准

- [ ] 用户能在移动端和桌面端创建并完成 16/32 首赛事；
- [ ] 前端不会直接请求外部音乐 Provider 或 Agent 服务；
- [ ] 开赛前候选不足/重复时，开始按钮不可用且有明确提示；
- [ ] 对局投票不会因重复点击产生重复提交；
- [ ] 刷新页面后服务端赛事状态正确恢复；
- [ ] 无试听、封面失效和 Agent 失败均具有可操作的降级体验；
- [ ] 赛事过程不显示模型内部推理或强行影响用户选择；
- [ ] 所有来源、推荐理由和报告边界可见；
- [ ] 全站不包含社交排行、公开赛事或敏感个人属性推断；
- [ ] 核心流程通过键盘操作和基础屏幕阅读器提示。

## 12. 不在本规格范围内

- 具体视觉品牌、Logo、插画、动效和设计稿；
- Java REST API 内部实现和 Agent SSE 生产实现；
- 原生 iOS/Android 客户端与酷狗 SDK；
- 用户账户注册、密码重置的具体页面；
- 国际化与多语言内容；
- 完整歌词、音频播放和任何社交功能。
