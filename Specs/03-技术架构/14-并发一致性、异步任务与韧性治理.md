# 并发一致性、异步任务与韧性治理

**状态：** 开发中
**最后更新：** 2026-08-28
**依赖：** `06-Java业务服务规格.md`、`09-Python报告Agent技术规格.md`、`13-Agent轨迹观测与质量评估体系.md`

## 1. 目标与边界

本规格将歌曲世界杯从单机异步调用升级为可恢复、可重试、可追踪的服务协作：Java 是唯一业务事实写入者；Python Agent 只产出受控结果；RabbitMQ 负责异步任务投递；Redis 负责短期互斥、幂等结果和热点缓存。

首期覆盖报告生成任务，候选池生成和偏好档案刷新复用同一任务模型。不会新增业务 Agent，也不会把 ReAct 决策改为固定流水线。

## 2. 一致性规则

| 场景 | 保证 |
| --- | --- |
| 投票 | 事务内完成 Vote、Match、下一轮槽位、赛事状态；`vote.match_id` 唯一，`match` 使用 `@Version`。重复幂等键返回原结果。 |
| 创建赛事 | 访客会话行锁 + `(guest_session_id, creation_idempotency_key)` 唯一；同键不同请求体返回 409。 |
| 确认候选池 | 使用幂等键与请求哈希；Java 在同一事务内校验候选、创建赛事与赛程。 |
| 生成报告 | 同一赛事、同一报告版本只允许一个有效 `PENDING/RUNNING` 任务；创建报告和写 Outbox 在同一 MySQL 事务提交。 |
| 消息消费 | 至少一次投递；消费者以 `report_id` 去重，状态转换幂等。绝不依赖“恰好一次”。 |

`match_id` 已是全局主键，因此不再增加冗余的 `(tournament_id, match_id)` 唯一约束；保留既有的 `(tournament_id, round_number, match_index)`，它才是对局位置的业务唯一性。

## 3. Outbox 与 RabbitMQ

```text
HTTP → Java Transaction
         ├─ tournament_preference_report(PENDING)
         └─ outbox_event(PENDING, REPORT_GENERATION_REQUESTED)
                 ↓ scheduled publisher
              RabbitMQ exchange → report-generation queue
                 ↓ consumer
              Java report worker → Python Agent → Schema 校验 → report READY/FAILED
```

- `outbox_event` 保存聚合类型/id、事件类型、JSON payload、状态、投递次数、下次投递时间与 traceId；禁止在数据库事务内直接调用 RabbitMQ。
- Publisher 仅将已提交的 `PENDING` 事件发布到 topic exchange；Broker confirm 成功后标记 `PUBLISHED`。失败采用指数退避，达到预算标记 `FAILED` 并告警。
- Queue 使用持久化消息、手动 ack、有限重试和死信队列（DLQ）。业务失败在有限自动重试后标记报告失败；基础设施失败交由 DLQ/重放处理。
- `CompletableFuture` 不再承担任何持久任务执行职责。SSE 只订阅任务状态/可展示进度，断线重连通过查询报告状态恢复。

## 4. Redis 规则

- `idem:{guestId}:{operation}:{key}`：短期幂等结果缓存；数据库唯一约束仍是最终事实。
- `lock:report:{tournamentId}:{version}`：报告消费者短期互斥，必须带 TTL，数据库状态是兜底。
- `cache:provider:{provider}:{hash}`：可缓存 MusicBrainz、搜索与目录查询；不得缓存 Cookie、API Key 或用户私有结果。
- `state:tournament:{id}`：热点赛事只读视图；任何写入后删除或更新。

## 5. 外部服务韧性

每个 Provider 独立配置 timeout、并发上限、重试和熔断，不能共享一个全局策略。

| Provider | 超时 | 重试 | 降级 |
| --- | ---: | --- | --- |
| DeepSeek | 90s（流式报告 320s） | 最多 2 次，仅可重试错误 | 标记任务失败，可由用户重试 |
| MusicBrainz | 8s | 2 次指数退避 | 切换在线发现来源/返回候选不足事实 |
| 博查/Tavily/国内研究 | 10–15s | 1–2 次 | Agent 自主选择其他工具 |
| RabbitMQ | 5s publish confirm | Outbox 重投 | 任务保持 PENDING |

使用 Resilience4j 的 TimeLimiter、CircuitBreaker、Bulkhead、Retry、RateLimiter；不得对非幂等写操作进行盲重试。记录 provider、动作、耗时、结果数量、HTTP 状态、限流/熔断/降级原因，但不记录密钥、Cookie、思维链或完整私有上下文。

## 6. 可观测性

- 每个入口生成或透传 `traceId`、`runId`、`conversationId`；HTTP Header 使用 W3C `traceparent`。
- Java 使用 Micrometer + Prometheus；Python 使用 OpenTelemetry SDK；RabbitMQ 消息 headers 透传上下文。
- OpenTelemetry Collector 接收 trace，Tempo 存储与查询；Grafana 展示 Prometheus 指标与 Tempo Trace。
- 首期仪表盘：任务成功率、P95 端到端耗时、队列积压/DLQ 数、候选池达标率、Provider 成功率/延迟/熔断次数、模型调用次数与估算成本。

## 7. 验收

1. 并发提交同一 vote：只有一条 Vote 与一次晋级；重试返回同一结果。
2. 并发请求同一报告：只有一个有效报告与一条待发布 Outbox 事件。
3. Java 在写入报告后、发布消息前重启：恢复后 Publisher 仍投递任务。
4. Agent 临时失败：任务按预算重试，最终状态与失败原因可查询，重复消息不生成第二份报告。
5. 单个 Provider 超时/熔断：Agent 可继续使用其他允许工具，指标记录降级原因。
6. 任意一次报告从 HTTP、RabbitMQ 到 Python 调用可按 traceId 查到完整链路；日志与 SSE 中无密钥、Cookie 或思维链。
