# Specs 文档导航

本目录按“先理解全局，再进入具体领域，最后落到可验收功能”的方式组织。目录名表示领域，文档文件名保留历史编号，避免已记录的引用失效；新文档不再使用全局连续编号。

## 阅读顺序

1. `00-总览与规范/00-系统总体设计与规格路线图.md`
2. `00-总览与规范/11-本地开发与部署规格.md`
3. `00-总览与规范/12-Docker本地排障手册.md`（本地启动异常时优先阅读）
4. `01-产品/03-MVP产品规格：歌曲世界杯与音乐探索.md`
3. 按开发任务阅读对应的数据、架构或功能规格。

## 目录职责

| 目录 | 内容 | 新文档规则 |
| --- | --- | --- |
| `00-总览与规范/` | 系统边界、开发约定、部署与文档导航 | 仅放跨领域的长期规范 |
| `01-产品/` | 用户场景、范围、交互与验收目标 | 以产品能力为单位 |
| `02-音乐数据/` | 数据来源、版权、实体匹配、知识库 | 以数据生命周期为单位 |
| `03-技术架构/` | Java、Agent、Web、可观测性等技术契约 | 以服务或横切能力为单位 |
| `04-功能规格/` | 可独立开发、测试和演示的功能闭环 | 按业务域建子目录；每篇包含目标、接口、数据、边界和验收 |

## 功能规格命名

新功能规格采用 `NN-功能名称.md`，其中 `NN` 只在同一业务目录内递增。例如：

```text
04-功能规格/
└── 歌曲世界杯/
    ├── 01-歌曲世界杯核心闭环.md
    └── 02-Agent探索候选池与赛后引导.md
```

当某个功能已有实现时，在对应文档顶部维护状态：`草案`、`开发中`、`已实现`、`已验证`。这样目录增长后仍可快速识别下一项工作。
